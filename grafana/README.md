# grafana/ — Grafana dashboards straight from Oracle (no Elastic)

The second optional way to visualise the suite. Where `elk/` ships documents
into Elasticsearch, this path leaves the data in Oracle: ORDS (Oracle REST
Data Services) exposes a handful of read-only views as JSON, and Grafana's
Infinity data source reads them. Nothing is copied anywhere, nothing writes
to Oracle, and the forecast and anomaly math stays in the views, which is
where the suite keeps it.

```
Oracle   CAPR_SERIES_POINTS / CAPR_HOURLY_POINTS / CAPR_FORECAST_POINTS / CAPR_FIT /
         CAPR_ANOMALIES / CAPR_ALERTS / CAPR_CONTAINER   (suite views, read-only)
   │
   ▼
ORDS     module awrcap: GET /ords/<schema>/awrcap/{containers,series,hourly,forecast,fit,anomalies,alerts}
   │     (grafana/ords/awrcap_module.sql; ORDS itself runs anywhere with JDBC access)
   ▼
Grafana  Infinity data source (JSON) + three provisioned dashboards
         (grafana/provisioning, grafana/dashboards, generated by grafana/build_*.py)
```

The endpoint contract is in [`API.md`](API.md). The same point views feed
`elk/export_capacity.sql` (all but `CAPR_HOURLY_POINTS`, which only this path
serves), so both paths show the same numbers by construction.

## When to pick this over `elk/`

- You have Grafana (or want it) and no Elastic stack.
- You want nothing between the dashboards and the database: every refresh
  is a live query against the views, so a new AWR snapshot shows up as soon
  as the daily views see it.
- You are fine running ORDS. It needs a JDBC route to the database and a
  one-time install that creates its own schemas (`ORDS_METADATA`,
  `ORDS_PUBLIC_USER`) in the container that holds the suite.

Pick `elk/` instead when the fleet is already in Elastic, when you want
history of the fits themselves (the ELK path snapshots fits and alerts per
day; this path shows the current fit only), or when ORDS is not an option.

## Install

1. **Suite views.** Already part of `install.sql` (`ddl/45_report_views.sql`,
   `ddl/55_report_views_ml.sql`). Reinstall the suite if it predates them.
2. **ORDS.** Install and run ORDS against the database. The lab recipe, with
   a dedicated installer user instead of SYS and ORDS in Docker, is in
   [`ords/README.md`](ords/README.md).
3. **REST module.** As the schema owner (or as a DBA with `ORDS_ADMIN`):
   ```
   SQL> @grafana/ords/awrcap_module.sql
   ```
   This ORDS-enables the schema and defines the `awrcap` module. Re-run to
   update; `awrcap_module_drop.sql` removes it.
4. **Grafana.** `docker compose -f grafana/docker-compose.yml up -d` starts
   Grafana (port 3001, Infinity plugin preinstalled, data source and
   dashboards provisioned from this directory, admin/admin kept for the lab,
   anonymous read-only viewing on) and ORDS (host port 8181, `ORDS_HOST_PORT`
   overrides). Point an existing Grafana at the same files instead if you
   have one: copy `provisioning/` and `dashboards/`, install the Infinity
   plugin, and set `ORDS_URL` to your module's base URL.

Open `http://<grafana>:3001/d/awrcap-tablespaces`, `/d/awrcap-cpu-series`,
`/d/awrcap-fleet-anomalies`. The three boards link to each other and carry
the database and series selection across.

## How the boards are built

Each dashboard is generated by a `build_*.py` (stdlib only) on top of
`dash_lib.py`. Every panel is an Infinity JSON query against one endpoint
with `${__from:date:iso}` / `${__to:date:iso}` and the `$db` / `$series`
variables; long rows are turned into one series per `db + series` with
Grafana's partition transformation, and forecast / band / ceiling series are
styled by name (dashed, dotted, grey). Anomalies arrive three ways: a
dashboard annotation query on `anomalies` (red vertical markers with the
message on hover, a shaded span for a level shift), red points on the
observed line where `anomaly = 1`, and red bars in the daily-growth panel.
Every anomaly row carries its baseline mode (`TRAILING`, `SAME_DOW`,
`HOUR_OF_WEEK`); the fleet board filters on it and colours its per-day bars
by it, and the CPU board's hourly panel draws the `hourly` endpoint with the
usual value for each hour of the week and the flagged hours in red. All
timestamps are the DB wall clock labelled `Z`; the boards run in UTC so they
show it unshifted (API.md).
Panels that need the same endpoint reuse each other's result through the
Dashboard data source, which keeps a page load to about a dozen ORDS calls.

## Security

The module is defined with no ORDS privilege, so the endpoints are readable
by anyone who can reach ORDS. That is right for a lab and wrong for
production: put ORDS behind your reverse proxy, or protect the module with
an ORDS privilege (OAuth client credentials or basic auth) and give the
Infinity data source those credentials. The views expose capacity numbers
and object names, never row data.

## Notes and limits

- **One schema per module.** The endpoints serve the schema the module is
  defined in, so a board shows the databases that schema's seam presents:
  one CDB with its PDBs in local mode, the whole fleet in warehouse mode.
  For several local-mode installs, define the module in each and add one
  Infinity data source per database, or use the warehouse seam.
- **Live queries.** Every refresh runs the CAPF_/CAPA_ views, whose
  self-joins and ESM lookups take seconds at fixture size (forecast and
  anomalies endpoints: 5 to 7 s here; a full board fills in 10 to 20 s).
  That is the price of having no copy; put a result cache or materialized
  views under `CAPR_*_POINTS` if it matters, or use `elk/` which snapshots.
- **ORDS concurrency.** The default pool refuses bursts (HTTP 429/555 beyond
  roughly ten in-flight requests). Raise `jdbc.MaxLimit` in the pool config
  for many simultaneous viewers.
- **Single-value filters.** `db` and `series` take one value server-side;
  multi-select and "All" are filtered inside Infinity after fetching the
  kind.
- **No fit history.** `fit` is the current fit only. The ELK path keeps a
  daily snapshot of fits and alerts; this path does not.
- **Lab only.** Anonymous viewer access, the default admin password and a
  public ORDS module are convenient on a workstation and wrong anywhere
  else; see Security above.

## Regenerating the dashboards

`grafana/dashboards/*.json` is generated; edit the `build_*.py` builder and
re-run it. Grafana's file provisioner picks changes up within its scan
interval.
