# apex/ — the capacity dashboards as an Oracle APEX application

The third optional way to look at the suite's numbers, and the only one
that needs nothing outside the database: no Elastic stack, no Grafana, no
REST module. The application is imported into an APEX workspace whose
parsing schema holds the suite, reads the `CAPR_*` views and `CAP_CONFIG`
of that schema, and draws them with APEX's own components (Oracle JET
charts, Interactive Reports, classic reports). No external JavaScript, no
copies of the data, and nothing in the suite's tables is ever written; the
only thing the app writes is its own session state (APEX collections).

```
Oracle   CAPR_SERIES_POINTS / CAPR_FORECAST_POINTS / CAPR_FIT / CAPR_ANOMALIES /
         CAPR_ALERTS / CAPR_CONTAINER + CAP_CONFIG          (suite views, read-only)
   │     loaded once per APEX session into AWRCAP_* collections
   ▼
APEX     application "AWR Capacity" (apex/awrcap_app.sql, generated by apex/build.py)
         pages: Overview, Tablespaces, CPU and workload, Fleet anomalies
   ▼
Browser  http://<ords-host>/ords/r/<workspace>/awrcap/overview
```

The same views feed `elk/` and `grafana/`, so all three paths show the same
numbers by construction (`grafana/API.md` documents the shapes).

## When to pick this over `elk/` or `grafana/`

- You already run APEX (it ships with every Oracle database since 19c; ORDS
  serves it) and want the dashboards next to the data with database
  authentication and no new moving parts.
- You want the operator's own ad-hoc analysis: every table here is an
  Interactive Report, so filtering, sorting, grouping and CSV download come
  for free.
- You do not need fleet-wide history of the fits themselves (the ELK path
  snapshots fits and alerts per day; APEX, like Grafana, shows the current
  fit).

Pick `grafana/` when Grafana is already the team's pane of glass, `elk/`
when the fleet is already in Elastic.

## Pages

| page | shows | filters that apply |
|------|-------|--------------------|
| Overview | alert counts by severity, the live alert list, worst days to full, total database size, data freshness | database |
| Tablespaces | days-to-full ranking, used space with the REGR projection (dashed), its band (dotted), the ceiling (grey) and anomaly days (red); daily growth with flagged days in red; growth anomalies; tablespace alerts | database, tablespace, date range |
| CPU and workload | host busy % and busy-hour p95 against the saturation line, DB CPU % per container with level-shift windows, CPU trend fits, SESSIONS / PROCESSES / DB size / redo against their limits with forecasts, workload fits, CPU and series alerts | database, date range |
| Fleet anomalies | anomalies per day by kind, most anomalous series, the anomaly timeline per series lane, the anomaly list with drill-downs, every alert | database, kind, severity, date range |

The filter bar lives on the global page, so a selection carries across
pages. A **Refresh data** button reloads the views; the **Data** badges next
to it show the latest observed day per database and when the data was
loaded, so an empty alert list is never mistaken for missing data.

## Install

Built and tested on APEX 26.2 (Oracle Database 23ai Free). The export uses
the 26.2 import API, so the target instance must run APEX 26.2 or later.

1. **Suite.** Install the suite (`install.sql`, any seam mode) in the schema
   that will be the application's parsing schema. The app needs the
   `CAPR_*` views from `ddl/45` and `ddl/55` (part of `install.sql`) and
   `CAP_CONFIG`.
2. **Workspace.** Create a workspace whose primary schema is that schema and
   at least one end-user account. From SQL*Plus as `SYSTEM` (or any user
   with `APEX_ADMINISTRATOR_ROLE`) in the PDB:
   ```
   SQL> @apex/workspace.sql AWRCAP AWRCAP
   ```
   It creates the workspace if missing, a developer account `ADMIN` and an
   end-user account `AWRCAP_VIEWER` (no App Builder, no SQL Workshop), and
   prompts for their passwords without echoing them (a blank password leaves
   an existing account untouched, so re-running is safe; for a
   non-interactive run pass the two passwords as arguments 3 and 4 with
   stdin from `/dev/null`, never piped). The APEX administration UI does the
   same thing by hand.
3. **Application.** As the parsing schema owner or an APEX administrator,
   from the `apex/` directory (the installer uses relative includes):
   ```
   cd apex
   sqlplus awrcap/...@//host:1521/pdb @install.sql AWRCAP AWRCAP 110
   ```
   Arguments: workspace, parsing schema, application id (defaults `AWRCAP`,
   `AWRCAP`, `110`). The installer refuses to overwrite an application id
   that belongs to another application or workspace, and re-running replaces
   the app in place (existing sessions of the app end).
4. **Open** `http://<ords-host>/ords/r/<workspace>/awrcap/overview`
   (workspace path prefix in lower case; the other page aliases are
   `tablespaces`, `cpu`, `anomalies`) and sign in with the end-user account.
   `f?p=110` works too.

Lab shortcut for the Docker instance described in `LAB.md`:

```sh
apex/publish.sh          # build.py -> docker cp -> install.sql inside the 23cfree container
```

Overrides: `APEX_CONTAINER`, `APEX_PDB`, `APEX_WORKSPACE`, `APEX_SCHEMA`,
`APEX_APP_ID`. The script never prints the container's `ORACLE_PWD`. After
publishing, run the smoke harness as the parsing schema from the `apex/`
directory: `sqlplus awrcap@... @test/apex_smoke.sql 110` (about 90 s; it
creates a scripted APEX session, loads every collection, runs every region
and LOV query under four filter scenarios, and checks each collection
against its source view; non-zero exit on any failure).

## How the app reads data

Every `CAPR_*` view is a live evaluation of the forecast and anomaly chain;
on the demo schema `CAPR_ANOMALIES` takes about nine seconds and
`CAPR_FORECAST_POINTS`, `CAPR_FIT` and `CAPR_ALERTS` two to four seconds each.
A page with half a dozen regions would re-run them half a dozen times, so
the app loads each view **once per session** into an APEX collection
(`AWRCAP_SERIES`, `AWRCAP_FORECAST`, `AWRCAP_FIT`, `AWRCAP_ANOMALIES`,
`AWRCAP_ALERTS`, `AWRCAP_CONTAINER`, plus `AWRCAP_META` with the load time
and the `CAP_CONFIG` thresholds) and every region reads the collection. A
page loads only the collections it needs, the first time it is opened in a
session; later visits are instant. On the demo schema the first Overview of
a session takes about 14 s (the anomalies view alone is 9 s), Tablespaces
adds about 4 s for the forecasts, and every later page view is 2 to 3 s.
**Refresh data** drops the collections and reloads them; the load time
(database clock) is shown in the **Data** badges. The loader is the
application process "Load data" (Before Header); it also fills the date
range (last observed day minus and plus 120 days) and, on the Tablespaces
page, picks the tablespace with the fewest days to full when none is
selected.

The CTE that maps collection slots back to named columns is generated once
from the registry in `build.py` and prepended to every region query, so a
column is defined in exactly one place.

## Security

APEX account authentication; the end-user account has no development
privileges. The app's SQL touches only the parsing schema's `CAPR_*` views,
`CAP_CONFIG` and the APEX collection API; it exposes capacity numbers and
object names, never row data. Grant the parsing schema nothing it does not
already have for the suite. Put ORDS behind TLS outside a lab.

## Notes and limits

- **Collections hold the whole view.** Fine for one database or a small
  fleet (the demo schema: 3,500 series points). For hundreds of tablespaces
  times a year of history the first page load of a session grows with the
  data; if that matters, materialize the `CAPR_*` views by a job and point
  the app's parsing schema at the copies (the open "results layer" item in
  the project's todo list).
- **Horizon 0 is the actual value**, horizons 30 and beyond are the fitted
  line. On a stepped series the dashed projection can start below today's
  value; that is the suite's forecast, not a drawing error.
- **ESM points are optional.** The +30 ESM marker appears only when a model
  is fresh (`cap_forecast_ml.train_all`, weekly retrain, 30-step cap); the
  charts never depend on it.
- **CPU reference lines.** The saturation line is `cpu_sat_pct` from
  `CAP_CONFIG` (80 by default). `CAPR_FIT.limit_value` for CPU is that
  threshold, while the point feeds carry 100; the app draws the line from
  the config value.
- **Host CPU is a root-container series.** OSSTAT records under the CDB's
  own `con_dbid`, so with a PDB selected the host CPU chart shows its CDB
  root's rows (the same host) rather than nothing. Local mode has no per-PDB
  DB CPU, sessions or redo either (see `CLAUDE.md`); fixture and warehouse
  data may.
- **Tablespace filter values are `database|tablespace`**, because tablespace
  names repeat across databases; "All tablespaces" draws only the observed
  lines (the projection, band and ceiling need one tablespace).
- **The anomaly timeline draws episodes.** Consecutive flagged days of one
  series and kind merge into one bar; a level shift spans its window.
  Colours are per kind (growth red, CPU amber, shift blue); a kind the app
  does not know keeps the chart's default colour, and the kind and severity
  filters list whatever values the data has.
- **A level shift is dated at the start of its window** (`ts`), with the
  window's last day in `obs_day`; the DB CPU chart shades that span.
- **Alerts are stateless.** `CAPR_ALERTS` is the current evaluation: no ids,
  no acknowledgement, no new/resolved. The alert tables are "what pages right
  now".
- **Region SQL keeps the suite's 19c floor** (inline window clauses, explicit
  formats), so the same export runs against a 19c database that hosts APEX
  26.2.

## Regenerating the application

`apex/awrcap_app.sql` is generated; edit `apex/build.py` and re-run
`python3 apex/build.py`. Component ids come from a fixed sequential
allocator, so a rebuild is byte-identical unless the builder changed, and
the file diffs like source. `python3 apex/build.py --smoke` writes
`apex/test/apex_smoke.sql`, which runs every region query inside a scripted
APEX session against the demo data; run it after changing a query.
