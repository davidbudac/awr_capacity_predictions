Tutorial

From zero to reading the report, in fifteen minutes

Install the suite, read your first report, run it every day, and learn what each number means. Every example on this page is real output from the sample report, and every command is one the repository ships.

The example database. The sample report comes from ECOMPRD, a fictional e-commerce CDB with one application PDB, SHOP_PDB, and 150 days of designed hourly AWR history. Its last day is 2026-10-17. The charts below replot the same daily values the report was computed from.

Step 1 ~1 min

The big picture

Five layers of views, stacked on AWR, inside the database.

AWR already writes a snapshot of every database every hour by default. The suite reads those rows and never writes to them. It stacks views on top: one layer cleans the snapshots into a daily series, the next fits a forecast and scores anomalies, and the last turns both into alerts. Click a stage, or let it run, to follow the tablespace AUDIT_TRAIL through it.

The prefix of a view name tells you its layer. Only the CAPV_ views read DBA_HIST_*, so the same layers run unchanged on a local AWR, on a central warehouse, or on the test fixture.

Step 2 ~2 min

Install

One script does the preflight, the install and the first report.

You need Oracle Database 19c or newer with the Diagnostics Pack (AWR is part of it), sqlplus, and a sysdba connection to CDB$ROOT, where the AWR history lives. On the database host:

DB host · bashyou run
git clone https://github.com/davidbudac/awr_capacity_predictions.git
cd awr_capacity_predictions
./quickstart.sh                      # sqlplus / as sysdba, CDB$ROOT

quickstart.sh runs three scripts in a row. doctor.sql is a read-only preflight that checks grants, retention and how much history each source has. If it reports a FAIL line, the quickstart stops before installing and tells you why. install.sql creates the views and packages in the current schema. report/report.sql spools the first report. The end of the output looks like this:

outputexpect
  All CAP* objects valid in schema SYS.
============================================================
 Install complete (seam_mode = local, schema = SYS).
============================================================
...
Report written to: reports/cap_report_CDB1_202609221410.txt
!

A fresh database says INSUFFICIENT_HISTORY. Stock AWR keeps 8 days and a forecast needs min_train_days (14) daily points. Raise the retention once; the forecasts fill in over the next weeks. This is optional and it is the only change the suite asks of Oracle.

SQL*Plus · CDB$ROOToptional · once
SQL> EXEC DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS(retention => 90*24*60);

As / as sysdba, the quickstart installs into SYS and install.sql warns you about it. That is fine for a first look. For a lasting install, create a dedicated owner once and install into it. Always start SQL*Plus in the repository root, because the @@ includes resolve from there.

SQL*Plus · CDB$ROOTproduction path
sqlplus / as sysdba
SQL> @create_owner.sql                           -- C##AWRCAP, direct DBA_HIST_* grants
SQL> ALTER SESSION SET CURRENT_SCHEMA = C##AWRCAP;
SQL> DEFINE seam_mode = 'local'
SQL> @install.sql                                -- idempotent; keeps knobs you changed
SQL> @report/report.sql

The suite writes only to its own CAP_* tables. To remove everything, run @uninstall.sql.

Read each alert row left to right:

SEV
CRIT, WARN or INFO. The list is sorted by it.
KIND
What kind of problem. TBSPC_FULL is a forecast (it will fill), TBSPC_NEARFULL is a level (it is full now), *_ANOM is an unusual day.
DB/PDB
The database and container. ECOMPRD alone means the root or host level.
MESSAGE
The number that tripped the alert and the number it was compared with.

Below section 0, every section holds the evidence for one family of alerts:

Report sections

The report is read-only. It only runs SELECT statements, so you can run it as often as you like.

Step 4 ~3 min

Day to day

A daily report, an alert feed with memory, and a drill-down when a number looks wrong.

Run the report on a schedule

report/run_report.sh is the cron wrapper. It runs the drivers from the repository root and exits non-zero when sqlplus fails or any ORA- or SP2- line appears, so cron mail tells you when a run broke.

crontab · oracleexample
30 6 * * * . /home/oracle/.bash_profile; /opt/awrcap/report/run_report.sh "/ as sysdba" --html --keep 14 >> /var/log/awrcap_report.log 2>&1

Add --schema C##AWRCAP when the suite lives in a dedicated owner, --csv for one CSV per section view, and --scope 3141592653:3141592654 to report on one container only. By hand, the same drivers are @report/report.sql, @report/report_html.sql and @report/report_csv.sql.

Poll the alerts

CAPR_ALERTS is section 0 as a view: one row per current issue. A monitoring tool can read it directly.

SQL*Plusexample
SQL> SELECT severity, kind, db_pdb, message
  2    FROM capr_alerts ORDER BY sev_rank;

-- alarm on the numbers, without parsing the message text
SQL> SELECT kind, db_pdb, series_key, value, threshold, unit
  2    FROM capr_alerts WHERE severity = 'CRIT';

Give the alerts a memory

CAPR_ALERTS is evaluated every time you query it and remembers nothing. cap_results.refresh stores each run and keeps one state per alert, keyed by a state_key that stays the same from day to day. Each run compares what it sees with the stored states and records an event.

SQL*Plusyou run
SQL> EXEC cap_results.refresh
SQL> SELECT severity, kind, db_pdb, message, age_days, events_since
  2    FROM capr_alerts_latest ORDER BY sev_rank;   -- open, not acked, as of the last run

-- acknowledge: hidden until the date (NULL = until it resolves)
SQL> EXEC cap_results.ack('TBSPC_FULL|3141592653|3141592654|AUDIT_TRAIL|-', SYSDATE + 7, 'disk ordered, CHG0042')

SQL> SELECT * FROM capr_alert_events WHERE run_id > :last_run_id;   -- poll the changes

An escalation or a reopen clears the ack, so a hidden alert comes back when it gets worse.

Let the scheduler do it

install_jobs.sql creates three DBMS_SCHEDULER jobs in the suite's schema, all disabled. Enable the ones you want:

SQL*Plus · suite owneroptional
SQL> @install_jobs.sql
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_REFRESH_JOB')       -- daily 01:30, cap_results.refresh
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_ML_RETRAIN')        -- daily 02:00, Tier 2 models
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_REPORT_SPOOL_JOB')  -- daily 03:00, alert snapshot file

CAP_ML_RETRAIN only matters if you use Tier 2. Train it once by hand with EXEC cap_forecast_ml.train_all (it needs CREATE MINING MODEL), and section 6 of the report fills in.

Drill into one series

When a row looks wrong, the drill-down prints everything behind it: the fit, every daily value with its fitted value and residual, the anomaly arithmetic, and the segments that grew the most.

SQL*Plus · repo rootyou run
SQL> @report/drill_tbspc.sql AUDIT_TRAIL 3141592654   -- tablespace, con_dbid (optional)
SQL> @report/drill_cpu.sql DB_CPU_PCT 3141592654

The same views also feed three optional dashboards: Kibana, Grafana over ORDS and an Oracle APEX app. They read the numbers this tutorial explains, so nothing below changes when you switch to one.

Step 5 ~3 min

Forecasts, bands and days-to-full

A straight line through 90 days, a band around it, and the day it meets the ceiling.

Take the CRIT row: AUDIT_TRAIL in SHOP_PDB. The daily series is the tablespace's used space at each day's last snapshot. Press replay to watch the 90 training days arrive, the line get fitted, and the projection run into the 130 GiB maxsize.

The fit is ordinary least squares over the last train_days (90) days. The projection starts at today's value, not at the end of the fitted line, so you can check every number with a calculator:

slope 613.664 MiB/day = 0.5993 GiB/day +30 days 119.60 + 30 × 0.5993 = 137.58 GiB (section 2: +30_GIB 137.58) days_full (130.00 − 119.60) / 0.5993 = 17.4 → 17 (section 1a: DAYS_FULL 17)

The shaded band is the 95% prediction band. It widens with distance, because the slope is uncertain and every day adds noise; at +180 days it is 214.58 to 240.35 GiB. WORST and BEST (16 and 18 days) come from the 95% confidence interval on the slope. A blank BEST means the interval includes zero growth, so the tablespace might never fill.

Now look at ACCEL 1.92 in section 1a. It is the slope of the last recent_days (28) divided by the 90-day slope. Above 1.5 means growth is speeding up. AUDIT_TRAIL tripled its daily growth in mid-September, which you can see as the bend in the chart. At the recent rate, 1.92 × 613.664 ≈ 1,178 MiB/day, the last 10.40 GiB lasts about 9 days, not 17. The Tier 2 value in section 6 agrees: its +30 estimate is 155.35 GiB, past the ceiling. Treat 17 days as the optimistic end. The report also prints what to do: NEED_90_GIB 54.40 (space to add so the upper band stays under the limit for 90 days) and ADD_BY 2026-11-02 (the worst-case fill date).

Quality grades

Not every line deserves trust. Each fit gets one grade, and only OK forecasts page.

Quality grades, with an example from the sample
GradeMeansSample
OKEnough history and a fit good enough to act on. Tablespaces need R² ≥ r2_gate (0.60); CPU needs a slope outside its own 95% interval.AUDIT_TRAIL, R² 0.916
LOW_CONFIDENCEThe line explains too little of the movement. Shown, never paged.none in the sample
FLATNo growth at all, so no fill date.PRODUCT_CATALOG, 12.00 GiB every day
CYCLICAt least cyclic_min_cliffs (2) purges in the window. Judged on its peaks, not the sawtooth.SESSION_STORE, purged every 30 days, peaks at 30.8%

CPU works the same way, with one difference: the projection starts at ANCHOR, the median of the last shift_days (7) complete days, because a single day of CPU is noisy. Host BUSY_P95 (the busy hour) has ANCHOR 69.62 and slope 0.2018 points per day, so (80 − 69.62) / 0.2018 = 51 days to the cpu_sat_pct (80) line. That is the CPU_SAT row in section 0.

Step 6 ~2 min

Anomalies and baseline modes

Is today unusual compared with days that should look like it?

An anomaly is a day (or, for CPU, an hour) that sits too far from a baseline. The baseline is a median of comparable past points, and "too far" is measured with the MAD (median absolute deviation), so one bad day in the history cannot drag the baseline with it. Here is the CPU_ANOM row from section 0: host CPU on Friday 2026-10-09, compared with the 8 Fridays before it.

MAD σ 1.4826 × median |x − 46.82| = 2.07, floored at cpu_min_mad_pct 3.00 threshold mad_k × σ = 3 × 3.00 = 9.00 points robust z (69.80 − 46.82) / 3.00 = +7.7 → |z| > 3 → HIGH

The floor matters. A very steady baseline has a tiny MAD, and without a floor every small wobble would flag. For tablespaces the floor is abs_floor_bytes (100 MiB per day).

Every point is scored against more than one baseline:

Baseline modes (report column MODE)
ModeCompares withRaises alerts by default
TRAILING · TRLThe last mad_window_days (28) days. "Unusual lately?"tablespaces, fixed-ceiling series
SAME_DOW · DOWThe same weekday over the last dow_weeks (8) weeks. "Unusual for a Friday?"CPU
HOUR_OF_WEEK · HOWThe same weekday and hour over those weeks, CPU only. "Unusual for Friday 10:00?"none (shown in section 5)

Which modes alert is set per family by the bitmask knobs alert_modes_tbspc, alert_modes_cpu and alert_modes_series (1 = TRAILING, 2 = SAME_DOW, 4 = HOUR_OF_WEEK). The report shows every mode; only the alerting ones reach section 0.

Two things in the sample show how the modes behave. First, a trailing baseline adapts. AUDIT_TRAIL's growth tripled on 2026-09-15; section 3 flags it under TRL until 2026-09-28, then stops, because by then the new rate fills half the 28-day window and has become the median. The lasting change is now the forecast's job (ACCEL 1.92). Second, consecutive flagged days collapse into one alert row: SHOP_PDB's DB CPU flagged on 13 days in a row and section 0 shows a single DBCPU_ANOM row, "13 consecutive days, latest 2026-10-17". Section 0 looks back anomaly_report_days (14) days; the report sections print the last 30.

Step 7 ~1 min

CPU level shifts

A step that stays, as opposed to a day that sticks out.

A release can raise CPU for good. A per-day anomaly would flag it every day until the baseline catches up. CAPA_CPU_SHIFT asks a different question: is the median of the last shift_days (7) days far from the median of the shift_baseline_days (28) before it? SHOP_PDB's DB CPU is the test case, and section 5b of the sample is empty. The chart shows why.

A shift is flagged UP or DOWN only when both conditions hold: the gap between the medians is more than shift_min_pct (15) percentage points, and every day of the recent window sits outside the baseline median ± its MAD σ. Here the second condition holds (all 7 days are above 14.98), but the gap is 22.96 − 11.98 = 10.98 points. So no CPU_SHIFT, and the step reaches you as the DBCPU_ANOM episode instead. If a 10-point step matters on your system, lower the knob:

SQL*Plus · suite ownertuning
SQL> UPDATE cap_config SET cfg_value = 10 WHERE cfg_name = 'shift_min_pct';
SQL> COMMIT;
SQL> SELECT * FROM cap_cfg_check WHERE status <> 'OK';   -- any knob MISSING or BAD?

When a shift is active, the per-day CPU anomalies inside it drop to INFO, so the shift row carries the news once. An UP shift is WARN; a DOWN shift is INFO.

Step 8 ~1 min

Freshness and severity

Is the data still arriving, and how loud should each finding be?

Two checks keep old data from looking current. Each forecast row carries is_current: N when its last day is more than stale_days (3) days behind the newest day of its database, as with a dropped tablespace. A stale row is shown but never pages; the report marks it GATE stale. That test compares the data with itself, so it cannot notice when AWR stops altogether. CAPR_FRESHNESS compares the newest snapshot with the clock instead, and DATA_STALE is listed first in section 0 when it is stale_hours (36) old. A database silent for data_stale_max_days (14) days is treated as retired and stops alerting.

The countdown kinds page only on an OK fit and a current series. The level kinds (NEARFULL, HOT) page at any quality, because full now is full whatever the trend says. That is why CUSTOMER_DATA warns at 95.0% although it grows 20 MiB a day and its fill date is 399 days out. When a row in the warning window does not page, section 1a says why in its GATE column: low-q, short, cyclic, stale or lim<used. LOW and shrink-side anomalies are INFO.
