How it works

Five view layers turn irregular AWR snapshots into forecasts, anomalies, alerts and a report, all built on one swappable data source.

Plain-English terms

A few words here come from software testing and data science, not infrastructure. Here's what each one means in terms you already use day to day.

Term you'll seeWhat it actually means
AWROracle's built-in performance history (Automatic Workload Repository) — the snapshots already sitting in your database. This tool only reads it; it never touches your data.
Seam  CAPV_ viewsA thin adapter / switch layer. Think of a symlink, or an alias in a load balancer: all the reporting math reads from these 9 views, and at install time you decide what they point at. Change the pointer, and everything above it keeps working unchanged.
Mode seam_modeWhich back-end the seam points at: local = this database's live AWR · warehouse = a central collector covering many databases · fixture = fake test data.
FixtureA set of fake, hand-built sample rows whose correct answers are known in advance — like a golden test file you diff against. You can't insert fake rows into real AWR, so fixtures are how the tool proves its math is right before you trust it on production.
HarnessThe self-check script that loads a fixture, runs the tool, and prints PASS/FAIL for each expected number. Same idea as a smoke-test script in CI.
Tier 1 (REGR)The always-on forecast: plain-SQL linear regression — a straight trend line you can reconstruct by hand. Transparent, nothing trained.
Tier 2 (OML / ESM)An optional second opinion using Oracle's built-in machine learning (Oracle Machine Learning). ESM = exponential smoothing, better at weekly seasonality. Off unless you turn it on.
MADMedian Absolute Deviation — a robust "how far from normal is this?" measure. Like standard deviation, but one huge spike doesn't wreck the baseline. Used to flag anomalies.
Baseline mode baseline_modeWhich past values count as "normal" for a point. TRAILING = the last 28 days. SAME_DOW = the same weekday in each of the last 8 weeks. HOUR_OF_WEEK = the same weekday and clock hour (CPU only). Every point is scored against each mode of its grain, and you choose which modes page you. Not the same thing as seam_mode.
Prediction bandThe uncertainty around a projection. Instead of "412 GiB in 180 days" you get a range the value should land inside 95% of the time — and days_to_full becomes "120 days, worst case 80".
Theil–SenA robust alternative to least squares: take the slope between every pair of days and use the median of them. One bulk-load day can move a least-squares line a long way; it can't move a median.
Change point / level shiftA step in the series rather than a trend: a purge that drops a tablespace by 600 GiB, or a workload move that leaves CPU permanently 18 points higher. Fitting one straight line across a step gives a fiction, so steps are detected and handled separately.
Backtest / holdoutHide the last few weeks, forecast them as if they hadn't happened, then score the forecast against what really occurred. MAPE is the average error as a percent; bias is the same average keeping its sign (positive = the engine over-forecast).
p95 / peak windowWays of saying "the busy hour" rather than "the daily average". p95 is the 95th percentile of the day's snapshot intervals; the peak window is the configured business-hours band.
IdempotentSafe to run again. Re-running the installer won't wipe your settings, overrides or trained models — it only fills in what's missing.
days_to_fullThe headline number: at the current trend, how many days until this tablespace hits its limit. Its cousins are days_to_sat (CPU) and days_to_limit (the fixed-ceiling series).

Architecture

The swappable data source (the "seam")

Write the reporting once, swap where the data comes from underneath it.

Every calculation in this tool reads from a thin layer of nine views prefixed CAPV_, shaped to look just like Oracle's AWR data dictionary. Nothing above them ever touches the real DBA_HIST_* tables directly. That single layer is the seam: to change where the data comes from, you swap one install file, and everything above it behaves identically: same math, same numbers. It's the database equivalent of pointing a hostname at a different server.

Architecture

Layer reference

What each layer is responsible for, and the non-obvious decisions baked into it. For the full column-by-column list, see the object index.

CAPV_  — seam views

Nine views re-present the AWR dictionary in a stable shape carrying (dbid, con_dbid). con_dbid is mandatory: TS# restarts at 0 per container, so SYSTEM in the root and in a PDB would collide without it. Block size rides on CAPV_TABLESPACE (populated for every tablespace); the datafile view is a fallback only, because DBA_HIST_DATAFILE is missing SYSTEM on stock 19c. Three of the nine are about identity and the newer series: CAPV_CONTAINER resolves each (dbid, con_dbid) to a database and PDB name (so reports print DB/PDB rather than a raw number), CAPV_RESOURCE_LIMIT carries processes / sessions utilisation against the init parameters, and CAPV_SYSSTAT carries the redo size counter.

CAPD_  — daily series

Tablespace usage is a level, so each day keeps the last sample (KEEP (DENSE_RANK LAST ...)) and converts blocks→bytes. UNDO/TEMPORARY are excluded, and the tablespace ceiling is resolved here — which is why operator overrides applied at this layer are honoured by everything above it. CPU BUSY/IDLE are cumulative counters — consecutive snaps are differenced per instance, and any interval spanning a restart (startup_time changed) or showing a negative delta is dropped. Deltas expose day_gap so a multi-day AWR gap becomes a rate, not a false spike. CAPD_SERIES_DAILY generalises the pattern: any series with a ceiling lands in one view keyed by a series name. CAPD_CPU_INTERVAL and CAPD_DBTIME_INTERVAL hold one row per valid interval, so the daily views and CAPD_CPU_HOURLY (host busy% and per-container DB CPU per clock hour, each bucket labelled by the hour its intervals end in) count exactly the same intervals.

CAPF_  — Tier 1 forecasts

Ordinary least squares over day_n = day_dt − DATE '2020-01-01' (optionally Theil–Sen — see forecast quality below). Two fits per series (a 90-day primary and a 28-day "recent"), giving an accel_ratio that flags accelerating growth — NULL rather than an absurd number when the slope is below accel_slope_floor_bpd. days_to_full = FLOOR((limit − cur_used)/slope). Quality is graded in priority order:

QualityCondition
INSUFFICIENT_HISTORYREGR_COUNT < min_train_days — too little AWR retention (or too few days left after a change-point reset)
FLATslope = 0. Note: REGR_R2 returns 1 for a flat series, not NULL, so flatness keys off the slope

CAPA_  — anomalies

Robust median + MAD, where MAD_σ = MEDIAN(|x − median|)·1.4826. CAPA_OBS lists every observation worth scoring: tablespace growth rates, host busy%, DB CPU per container (per day and per hour), and the fixed-ceiling series. CAPA_ANOM scores each one against every baseline mode of its grain, in two passes (median, then MAD about it), always excluding the point itself so a spike can't inflate its own baseline. CAPA_ANOM_DAY rolls the day modes up to one row per observation. Every flag carries value, median, threshold, robust z and the baseline size for hand-verification. How the modes differ, and how you pick which ones page you, is in Anomalies: three baselines. A separate view, CAPA_CPU_SHIFT, answers a question a per-point flag cannot. See CPU: peak, share and shifts.

CAPR_  — integration

The layer the outside world reads: display labels, pollable alerts, and one view per report section. Covered in the integration layer below.

Tier 1 in depth

Forecast quality: anchors, bands, robustness, resets, cycles, backtests

Several independent mechanisms sit on top of the plain linear fit. Each one is a CAP_CONFIG knob away from being turned off.

Anchored at today

A fitted line rarely passes through the last observation, so a projection read off the line can sit below today's usage while days-to-full says the tablespace fills next week. Every projection therefore starts at the current value: proj_h = cur_value + slope · h, with the band's half-width from the fit drawn around that anchor. The +30 column and days_to_full now tell the same story. For CPU the anchor is anchor_value, the median of the last shift_days complete days, so one odd day does not move every projection.

Three guards keep the numbers honest. days_to_full and its range clamp at 0, and limit_below_used = 'Y' says when the ceiling sits under the usage (an override set too low). Every CAPF view carries newest_day and is_current: a series whose last day is more than stale_days (3) behind its source's newest day, such as a dropped tablespace or a retired database, reads is_current = 'N' and stops raising forecast alerts. CPU and redo fits use complete days only (is_complete = 'Y': at least complete_day_pct, 80%, of the day covered by valid intervals), so a restart or an outage does not drag the line down.

Prediction bands — how wrong could this be?

A projection with no uncertainty attached invites false precision. Every CAPF_ fit therefore publishes a 95% band alongside each point projection, derived from the residuals of the same fit: the residual standard error is resid_se = √(SSE/(n−2)), and the half-width at a horizon x₀ is t · resid_se · √(1 + 1/n + (x₀−x̄)²/SXX). The band widens the further out you look.

The same machinery turns days_to_full into a range. The slope gets its own confidence interval (slope_ci = t · resid_se / √SXX); dividing the remaining headroom by slope + slope_ci gives the worst case (fastest plausible growth) and by slope − slope_ci the best case — NULL when the slow edge of the interval is not positive, i.e. "it might never get there". That's what the reports print as "120 days, worst case 80".

i

No t-distribution in SQL. Oracle has no TINV, so t is approximated as 1.96 + 2.4/df with df = n − 2. That's good to about 1% for df ≥ 10, and min_train_days guarantees df ≥ 12 before any band is published. The formula is part of the contract — the fixture harness recomputes the expected bands with the identical expression.

Theil–Sen — a slope one bad day can't move

Least squares minimises squared error, so a single step — a bulk load, an import, a partition drop — drags the whole line with it. The Theil–Sen estimator is the median of the pairwise slopes (y_j − y_i)/(x_j − x_i) over every pair in the training window: a minority of stepped pairs cannot move a median (its breakdown point is 29%). Cost is O(n²), about 4,000 pairs per series at the shipped 90-day window, computed with a self-join.

The slope_method knob (0 = OLS, the default; 1 = THEILSEN; 2 = DRIFT, below) decides which estimator the row uses, and a column of the same name says so. The Theil–Sen self-join runs only when it is selected, so ts_slope_bpd is NULL under the default and the fits stay cheap. When Theil–Sen is selected it drives the slope, the intercept, every projection, days_to_full / days_to_sat, both halves of accel_ratio and the slope = 0 FLAT test. It applies to tablespaces and to the CPU trend alike.

!

The bands stay OLS. There is no closed-form prediction interval for Theil–Sen in SQL, so r2, resid_se, the projection bands and slope_ci remain least-squares residual quantities — drawn around the chosen line. With the default slope_method = 0 nothing about the output changes at all.

Drift — when the daily rate itself wanders

A line assumes the residuals are noise around a fixed trend. Some series behave more like a random walk: the daily growth rate wanders, and an OLS band that narrows with more history is too confident. With slope_method = 2 the slope is the median of the daily rates, and the band grows like a random walk: t · (sd · √h + h · se), from the standard deviation of the rates and the standard error of their mean. Quality comes from the slope's confidence interval. drift_slope_bpd / drift_sd_bpd are exposed on every fit whatever the knob says, and CAPF_BACKTEST scores DRIFT too, so you can compare before you switch.

Change-point reset — don't fit across a purge

After a purge, archive or partition drop, a tablespace's history has a cliff in it, and a line fitted across the cliff understates the slope and overstates the headroom. With reset_on_shrink = 1 (the default) the training window restarts at the most recent day whose day-over-day delta is a large negative step:

the ruleM9.3
delta < -GREATEST(shrink_mad_k * MAD_sigma(window deltas), abs_floor_bytes)

The abs_floor_bytes term stops an exactly-flat series (MAD = 0) from treating every wiggle as a cliff, and shrink_mad_k defaults to 6 — twice the anomaly mad_k — because this restarts a fit and should only fire on real cliffs. The cliff day itself is day 1 of the new window (its used_bytes is already the post-purge level), so train_start = reset_day and the fit sees only post-cliff data. Both columns are published — reset_day is NULL when nothing reset — and if fewer than min_train_days rows survive, the quality honestly reads INSUFFICIENT_HISTORY: we genuinely don't know the post-purge growth rate yet. This is a tablespace mechanism only; a CPU step is a level shift, handled by CAPA_CPU_SHIFT.

Cyclic tablespaces — judged on their peaks

A tablespace with rolling retention climbs for a month, gets purged, and climbs again. The reset above would fit only the latest climb and page every cycle. When the training window holds cyclic_min_cliffs (2) or more cliffs, the series is graded CYCLIC instead: no reset, and the question becomes whether the peaks are growing. cycle_n, cycle_days, cycle_peak_pct and peak_slope_bpd (a line through the per-cycle maxima) describe it, and days_to_full comes off the peak line only when the peaks grow. TBSPC_FULL fires on that peak line. The demo's SESSION_STORE is one: 30-day cycles peaking at 30.8% of its limit, so it raises nothing.

Backtest — score the engines against what actually happened

CAPF_BACKTEST hides the last backtest_holdout_days (default 28) of each series, fits the training window ending at that cutoff, and scores the predictions against the days it hid: MAPE (average absolute error as a percent) and bias (the same average with its sign, so positive means the engine over-forecast), per series per engine. The REGR row is recomputed in pure SQL and is always available, anchored the way the live fit is (the last value for a tablespace, the median of the last shift_days days for CPU, incomplete CPU days left out); the ESM row appears once cap_forecast_ml.train_backtest has trained purpose = BACKTEST twin models through the same cutoff. Those twins never leak into the live forecast views. Because the 19c 30-step cap and a conservative FLOOR(rows/4) floor also apply to the twins, ESM may be scored on fewer days than REGR — n_days reports what each engine was actually scored on.

The backtest also decides something. With esm_tbspc_model = 2 (AUTO, the default) and esm_select_by_backtest = 1, each tablespace gets both candidate twins trained — EXSM_HOLT and EXSM_ADDWINTERS with a 7-day season — scored in CAPF_ESM_CANDIDATE, and the production model is built with whichever had the lower holdout MAPE (ties, or no evidence, go to Holt). Setting the knob to 0 or 1 pins a model type and skips the extra trainings; setting esm_select_by_backtest = 0 makes AUTO fall back to Holt.

CPU in depth

CPU: peak, share and shifts

A daily average hides the hour that actually saturates, and a trend line can't see a step. Three additions fix both, and a fourth stops AWR gaps from lying.

The busy hour, not the day

CAPD_CPU_DAILY keeps the day's time-weighted average (busy_pct) but adds the numbers that matter for headroom: busy_p95 and busy_max over the day's snapshot intervals, and busy_peak_pct, the time-weighted average inside a configured business-hours window. Membership in that window is decided by the interval's end hour falling in (peak_hour_from, peak_hour_to] — with hourly AWR and the default (8, 18], that's exactly the snapshots ending 09:00 through 18:00.

CAPF_CPU_TREND fits six metrics per container — BUSY_PCT, BUSY_P95, BUSY_PEAK, DB_CPU_SEC, DB_CPU_PCT and DB_CPU_P95 — each with the same bands and quality ladder as the tablespace fit. Every percent-of-capacity metric gets a days_to_sat against cpu_sat_pct (default 80); DB_CPU_SEC has no fixed ceiling, so its is NULL. The CPU_SAT alert keys off the p95 busy-hour trend unless you set cpu_sat_on_p95 = 0.

DB CPU as a share of the machine

Host busy% tells you the machine is hot; it doesn't tell you which container made it hot. CAPD_DBTIME_DAILY converts the time-model counters into two comparable percentages: db_cpu_pct — 100 · db_cpu_sec / (cpu_ceiling · interval seconds) summed per day, where cpu_ceiling = LEAST(NUM_CPUS, cpu_count): the fraction of the host's logical-CPU seconds this container's foreground DB CPU consumed. Oracle accrues CPU per logical CPU and AWR's own %Total CPU uses NUM_CPUS, so dividing by cores would read twice as high on an SMT host. It is on the same scale as busy% and therefore forecastable the same way — and host_share_pct, DB CPU seconds over the host's busy seconds that day: how much of what the host was doing was this container. The per-interval p95 / max / peak-window twins exist too, giving each PDB its own busy hour. A trend crossing the saturation line raises the DBCPU_SAT alert.

i

Why OSSTAT is CDB-wide, and where per-PDB DB CPU comes from. Host CPU is recorded under the CDB's con_dbid. In CDB$ROOT, DBA_HIST_SYS_TIME_MODEL holds one CDB-wide row per snapshot too; the per-container rows are in DBA_HIST_CON_SYS_TIME_MODEL, which the seam reads (the root row is then CDB$ROOT alone). That's what makes host_share_pct meaningful — and why the host busy seconds in its denominator are summed across the dbid, not read per PDB.

Is the CPU trend real? The significance gate

CPU has a weekly rhythm. A weekday / weekend host fitted with a straight line has most of its variance in that rhythm, so R² stays low even when the load is clearly growing, and the forecast reads LOW_CONFIDENCE. Two knobs, both on by default, fix that. cpu_deseason = 1 subtracts the weekday and weekend means (and adds back the window mean) before the fit (deseasoned says it did). cpu_quality_gate = 1 grades the fit OK when the slope is significant, |slope| > slope_ci (slope_sig), instead of asking for R² ≥ r2_gate; set it to 0 for the old rule.

A forecast also needs the host to still have headroom. hot_now = 'Y' when the median of the recent daily p95 (recent_p95_med) is already at or above cpu_sat_pct. That raises CPU_HOT (host) or DBCPU_HOT (a container) at any fit quality: a host that is saturated today needs no days-to-saturation.

Level shifts — the step a trend line can't see

A container that has run 18 points hotter since a workload moved onto it flags for its first few days at most: then the step becomes its own baseline and the per-point modes go quiet. The trend fit is too noisy to say so either. CAPA_CPU_SHIFT therefore compares windows: for each (container, metric) — BUSY_PCT, BUSY_P95 and DB_CPU_PCT — it takes the median of the last shift_days (7) days against the median of the shift_baseline_days (28) immediately before it. Since all three metrics are percentages, shift_pct is their difference in percentage points, never a ratio.

An UP flag needs all four of: the shift exceeding shift_min_pct (15 points); a full recent window; enough baseline days; and an N-of-M confirmation — every day of the recent window above base_med + MAX(base_mad_sigma, cpu_min_mad_pct). That last rule is what separates a genuine step from one loud day dragging a 7-day median: a single spike moves a median but cannot put all seven days over the line. DOWN is the mirror image (informational — workload left, or a container moved off). Every input is exposed, so a flag can be re-derived by hand, and the row exists even when nothing is flagged: it is the current state of the series, one row each, so a poller can read it unconditionally. BUSY_PEAK is deliberately excluded — it moves with BUSY_PCT's busiest hours and would only duplicate the alert.

AWR gaps don't get to lie

A missing stretch of snapshots doesn't leave a hole in a counter series — the next snapshot simply differences against a much older one, and that single long interval is attributed to the day it ends on. A 36-hour average is not a day, and it is certainly not a peak hour. So both CPU daily views publish max_interval_hours, day_gap and a gap_flag that is 'Y' when any interval of the day is longer than cpu_gap_hours. The day stays in the series (it is still data, and the forecast wants it), but the percentile and peak-window figures are computed only from intervals within the limit, and both CAPA_ANOM (in every mode) and CAPA_CPU_SHIFT refuse to score a gap day or let it into a baseline. The hour grain applies its own rule, described in Anomalies: three baselines.

!

Why the default is a loose 12 hours. The flag suppresses anomaly scoring, so an over-sensitive value doesn't make the tool careful — it silences the whole CPU anomaly layer on any site whose snapshot intervals are wide.

Generic series

Anything with a ceiling

Tablespaces aren't the only thing that fills up. One generic pair of views covers the rest — and any future one — with no new code.

CAPD_SERIES_DAILY is keyed by a series name and carries (dbid, con_dbid, series, day_dt, value, limit_value, unit, n_samples). CAPF_SERIES_FORECAST then applies deliberately plain OLS with the same M9.1 bands and the same quality ladder, and adds days_to_limit — with the one difference that the ceiling isn't a global percentage knob but a per-series limit_value carried up from the daily view. A fourth series would cost a UNION ALL branch and nothing else.

Anomalies in depth

Anomalies: three baselines

"Unusual" depends on what you compare against. Each point is scored against every baseline of its grain, side by side, and a bitmask decides which of them pages you.

A bulk load is unusual against the last four weeks of tablespace growth. A busy Monday is not unusual for a Monday, even when it is twice the Sunday before it. A day whose average is normal but whose hours are inverted (busy at night, idle at noon) is unusual only hour by hour. One engine answers all three questions, because a baseline mode only chooses which past values form the reference set. The median, MAD, threshold floor and flag rule are the same for every mode and every series.

One flag rule

A point flags HIGH (or LOW) when it sits more than mad_k · eff_sigma above (or below) the baseline median, where eff_sigma = GREATEST(MAD_σ, floor / mad_k). The floor is per unit and grain: abs_floor_bytes (100 MiB/day) for tablespaces, 9 points for a CPU day (mad_k · cpu_min_mad_pct), 15 for a CPU hour (cpu_min_mad_pct_hour, because hourly values are noisier), series_floor_count and series_floor_gib for the fixed-ceiling series. So a perfectly flat baseline still flags a real jump, sub-floor wiggles never flag, and |robust_z| > mad_k means flagged, always. For tablespaces and host busy% this is exactly the pre-M15 rule.

Gaps never vote

A gap row is never scored and never used as a baseline, in any mode. At day grain that is the cpu_gap_hours rule and every incomplete day (first day, today, restart day). At hour grain an interval of zero hours or less (a DST change or clock step), or one longer than LEAST(cpu_gap_hours, hour_gap_ratio × the usual interval), makes its hour a gap. DB_SIZE_GB also treats a day whose tablespace set changed as a gap: when a tablespace appears or drops out, the total moves by its whole size, which is membership, not growth.

You choose what pages

Every mode is always computed and shown in the report and in CAPR_ANOMALIES. Three bitmask knobs decide which modes raise a CAPR_ALERTS row: add 1 for TRAILING, 2 for SAME_DOW, 4 for HOUR_OF_WEEK. The defaults keep the paging you had before: alert_modes_tbspc = 1 (tablespaces on TRAILING), alert_modes_cpu = 2 (CPU and DB CPU on SAME_DOW) and alert_modes_series = 1. Set alert_modes_cpu = 6 to page on both weekly modes; an hour-of-week day then raises one row carrying its worst hour and the number of hours flagged.

i

Times are the database's wall clock. AWR records local time, the hour buckets use it, and the same weekday one week back is ts − 7 on the clock you read in AWR, across a DST change too. Every export labels these times with a Z and the dashboards run in UTC, so a chart shows exactly that clock.

Operator input

When the recorded limit isn't the real one

The autoextend maxsize in AWR is a promise the storage may not be able to keep.

A 32 GiB maxsize on a 10 GiB filesystem or diskgroup is not 32 GiB of headroom, and a days_to_full computed against it is a comfortable lie. CAP_TBSPC_OVERRIDE — the third persisted table — lets you state the ceiling that actually exists, and silence the staging tablespace that is supposed to fill up:

ColumnEffect
limit_bytesReplaces the computed ceiling for that tablespace.
exclude_flag'Y' drops the tablespace from the whole pipeline — no forecast, no anomaly, no alert, no report row.
dbid / con_dbid0 is a wildcard meaning "any", so one row can be a fleet-wide rule; the most specific matching row wins (a real dbid first, then a real con_dbid). tablespace_name is matched exactly — no patterns.

The resolution happens once, in CAPD_TBSPC_DAILY, which is why forecasts, anomalies, alerts and both reports honour it with no further code — including DB_SIZE_GB, which sums that view. CAPF_TBSPC_FORECAST.limit_source then reports which rule produced the ceiling in use: OVERRIDE, AUTOEXTEND (the datafile maxsize) or ALLOCATED (the current allocated size, when the files can't extend). Your rows survive @install.sql and are removed only by @uninstall.sql.

The top layer

The integration layer

CAPR_ exists so that monitoring systems and the two report drivers all read the same rows.

CAPR_ALERTS is the machine-readable surface: one row per current issue, with a severity (CRIT / WARN / INFO) and sort rank, a kind, the (dbid, con_dbid) keys plus the resolved db_pdb label from CAPR_CONTAINER, the metric value against its threshold, and a ready-to-page message. The kinds are TBSPC_FULL, TBSPC_NEARFULL, TBSPC_ANOM, CPU_SAT, DBCPU_SAT, CPU_HOT, DBCPU_HOT, CPU_ANOM, DBCPU_ANOM, CPU_SHIFT, SERIES_LIMIT, SERIES_NEARLIMIT, SERIES_ANOM, DATA_STALE (no AWR snapshot for stale_hours: the dead-man check) and MODEL_HEALTH (a failed or stale Tier 2 model). Forecast kinds take their severity from CAPR_SEVERITY, computed once for the report, the fit feed and the alerts, and need a current series. Each row also carries a per-row alert_key and a state_key that stays the same from day to day (kind, keys, series, mode). Anomaly kinds window on the anomaly_report_days knob (14), a different window from the report's own presentation knob, and carry the baseline_mode that raised them. Their rows come from CAPR_ANOMALIES, the one view that decides an anomaly's severity, message and whether it pages, so the report, the pollers and the dashboards always agree. Consecutive flagged days of one series and mode arrive as one episode row (first_day, n_days, max_z), and a per-day CPU anomaly inside an active level shift drops to INFO.

SQL*Pluspoll it
SQL> SELECT severity, kind, db_pdb, message FROM capr_alerts ORDER BY sev_rank;

Alongside it sits one view per report section — CAPR_TBSPC_DAYS_TO_FULL, CAPR_TBSPC_FORECAST, CAPR_TBSPC_ANOMALIES, CAPR_CPU_TREND, CAPR_CPU_ANOMALIES, CAPR_CPU_SHIFTS, CAPR_ESM_COMPARE, CAPR_BACKTEST, CAPR_SERIES and CAPR_SERIES_ANOMALIES. Every unit conversion, severity marker, ranking and display label is computed once, in the view. The text and HTML drivers only format what those views hand them (the HTML driver computes chart geometry and nothing more), so the two reports cannot show different numbers — and neither can disagree with what pages you. The three views that depend on Tier 2 load after the ML file, in ddl/55_report_views_ml.sql.

The ranking columns are how the drivers stay thin: severities and ranks such as rank_dtf, rank_report and is_reportable live in the view, so applying top_n or "only tablespaces that are growing, near-full, or at least report_min_gb GiB" is a plain WHERE clause in both drivers. The full column list is in the object index.

Memory: the results layer

CAPR_ALERTS is evaluated live, so on its own it cannot say "new since yesterday" or "someone already looked at this". The optional results layer adds that memory. cap_results.refresh, run by hand or by the disabled-by-default CAP_REFRESH_JOB, records a run in CAP_RUN, copies CAPR_FIT into CAP_FIT_HIST, and merges CAPR_ALERTS by state_key into CAP_ALERT_STATE, writing an event for each change: NEW, ESCALATED, DEESCALATED, RESOLVED (after resolve_grace_runs runs without it) and REOPENED. A failed run is recorded FAILED and re-raised, so the scheduler shows it too.

SQL*Plusstate, ack, digest
SQL> EXEC cap_results.refresh
SQL> SELECT severity, kind, db_pdb, message, age_days FROM capr_alerts_latest;
SQL> EXEC cap_results.ack('<state_key or alert_key>', SYSDATE + 7, 'disk ordered')
SQL> SELECT * FROM capr_weekly_digest;

CAPR_ALERTS_LATEST lists the open states that nobody acked, as of the last run, in a fraction of the time the live view takes. An ack lasts until its date, or until the alert resolves when you pass NULL; an escalation or a reopen clears it. CAPR_ALERT_EVENTS is the change feed to poll (WHERE run_id > :last). CAPR_WEEKLY_DIGEST compares the latest run with the one digest_days (7) earlier: days to full then and now, and the alerts that opened or resolved in between. CAPR_FORECAST_ACCURACY replays what each stored fit projected against what happened. Both report drivers can read the last run instead of the live views (the SNAPSHOT argument), which is fast.

Architecture

Two engines, side by side

A fully auditable baseline and a seasonality-aware second opinion.

Tier 1 · always on

Pure SQL — a straight trend line

Linear regression, or Theil–Sen when you select it. Every forecast is just slope × days + starting point, every band comes from the fit's own residuals, and every anomaly is explained by its median and MAD — so you can check any number by hand. Nothing to train, nothing hidden.

Reaches: +30 / +90 / +180 / +365 days, with 95% bands Needs: nothing beyond the views
Tier 2 · optional

OML ESM — exponential smoothing

One model per series via DBMS_DATA_MINING. CPU uses additive Winters (weekly seasonality); tablespaces default to AUTO, where the backtest picks between Holt and additive Winters per series. Shown against Tier 1 in section 6, and scored in 6c.

Reaches: its furthest step, at most +30 (19c hard-caps the horizon at 30 steps; 90 days of history give 22) Needs: CREATE MINING MODEL
!

The 30-step cap is real. Oracle 19c rejects EXSM_PREDICTION_STEP above 30 at any series length (verified: 30 valid, 31 fails at 121/300/600 rows), and the package also caps it at a quarter of the series length. So ESM never goes past +30 days: CAPF_COMPARE puts the model's furthest step (esm_horizon_days) in the +30 bucket and drops it once the model is older than esm_max_age_days (7), and +90/+180/+365 come from Tier 1 alone. The same cap is why an ESM backtest twin may be scored on fewer holdout days than its REGR counterpart. A failed build keeps the previous model and is reported (MODEL_HEALTH), and the retrain job runs daily.

Tier 2 is trained only where it makes sense: a series must grade OK or LOW_CONFIDENCE before a model is built, so a flat or near-full-but-static tablespace gets none.
