In-database · Oracle 19c floor · read-only

Capacity forecasting that lives inside the database.

SQL-level growth forecasting and deterministic anomaly detection driven entirely by AWR history — no external ML stack, no agent, no data export. Just views, one small config table, an OML package, and a read-only SQL*Plus text report.

5 view layers 6 seam views 2 persisted tables 2 forecast engines read-only against AWR safe to re-run

This suite turns the performance history Oracle already collects (AWR) into forward-looking capacity answers, without moving a single row out of the database. Everything runs as SQL and PL/SQL you can read, and every number it prints can be reconstructed by hand. Start here for the big picture, then follow the guides to install it, run it, and prove it against known answers.

How it works, in one idea

Write the analytics once, swap the data source underneath

The whole design hangs on a single trick called the seam.

Every calculation reads from a thin layer of six views prefixed CAPV_, shaped to look just like Oracle's AWR data dictionary. Nothing above them ever touches the real DBA_HIST_* tables directly. That single layer is the seam: to change where the data comes from, you swap one install file — and the identical SQL then runs against this database's live AWR, a central fleet warehouse, or synthetic test fixtures, producing the same math and the same report either way. It's the database equivalent of pointing a hostname at a different server.

▸

The one idea to hold onto. Point the seam at real AWR to report on production; point it at fixtures — fake data whose exact answers are worked out in advance — to prove the tool is correct. Same code either way. The How it works page walks the full pipeline built on top of it.

Forecasting

Two engines, side by side

A fully auditable baseline, and an optional seasonality-aware second opinion.

Tier 1 · always on

Pure SQL — a straight trend line

Standard linear regression (REGR_*). Every forecast is just slope × days plus a starting point, and every anomaly is explained by its median and MAD — so you can check any number by hand. Nothing to train, nothing hidden.

Reaches: +30 / +90 / +180 / +365 days Needs: nothing beyond the views
Tier 2 · optional

OML ESM — exponential smoothing

One Oracle Machine Learning model per series via DBMS_DATA_MINING. Tablespaces use Holt (trend); CPU uses additive Winters (weekly seasonality). Shown against Tier 1 in the report.

Reaches: +30 only — 19c hard-caps the horizon at 30 steps Needs: CREATE MINING MODEL
Trust

Safe by design

Two properties make this comfortable to install on a database you care about.

i

Read-only against your data. The report and all CAPV / CAPD / CAPF / CAPA views only ever SELECT. The suite writes exactly two tables of its own — CAP_CONFIG (tuning knobs) and CAP_ML_MODEL (the Tier 2 registry) — and nothing else.

▸

Safe to re-run. Re-running the installer is idempotent and non-destructive: your config overrides and trained models survive @install.sql. A full teardown is a single @uninstall.sql.
