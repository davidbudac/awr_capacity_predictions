In-database · Oracle 19c floor · read-only

Capacity forecasting that lives inside the database.

SQL-level growth forecasting, pollable alerts and deterministic anomaly detection driven entirely by AWR history — no external ML stack, no agent, no data export. Just views, three small tables of its own, an OML package, and read-only SQL*Plus reports in text and HTML.

5 view layers 9 seam views 3 persisted tables 2 forecast engines read-only against AWR safe to re-run

This suite turns the performance history Oracle already collects (AWR) into forward-looking capacity answers, without moving a single row out of the database. Everything runs as SQL and PL/SQL you can read, and every number it prints can be reconstructed by hand. The pipeline is five view layers deep — CAPV_ (seam) → CAPD_ (daily) → CAPF_ (forecast) → CAPA_ (anomaly) → CAPR_ (integration) — and the top layer is what both reports and any monitoring system read. Start here for the big picture, then follow the guides to install it, run it, and prove it against known answers.

How it works, in one idea

Write the analytics once, swap the data source underneath

The whole design hangs on a single trick called the seam.

Every calculation reads from a thin layer of nine views prefixed CAPV_, shaped to look just like Oracle's AWR data dictionary. Nothing above them ever touches the real DBA_HIST_* tables directly. That single layer is the seam: to change where the data comes from, you swap one install file — and the identical SQL then runs against this database's live AWR, a central fleet warehouse, or synthetic test fixtures, producing the same math and the same report either way. It's the database equivalent of pointing a hostname at a different server.

▸

The one idea to hold onto. Point the seam at real AWR to report on production; point it at fixtures — fake data whose exact answers are worked out in advance — to prove the tool is correct. Same code either way. The How it works page walks the full pipeline built on top of it.

Honest numbers

Forecasts that admit what they don't know

A single projected number is a guess dressed up as a fact. Four features keep the arithmetic honest.

Forecast-quality features
FeatureWhat it changes
Prediction intervalsEvery projection carries a 95% band, and days_to_full / days-to-saturation come as a worst-case / best-case range ("120 days, worst case 80") derived from the confidence interval on the slope.
Robust slopeTheil–Sen — the median of the pairwise slopes — is computed alongside ordinary least squares and can be selected with the slope_method knob, so one bulk-load day can't drag the whole trend.
Change-point resetAfter a purge or partition drop, the training window restarts at the cliff instead of fitting a line straight across it. The reset day is reported, so you can see it happened.
BacktestThe last few weeks are held out, both engines forecast them, and the report scores MAPE and bias per engine — which also picks the ESM model type automatically.
Forecasting

Two engines, side by side

A fully auditable baseline, and an optional seasonality-aware second opinion.

Tier 1 · always on

Pure SQL — a straight trend line

Standard linear regression (REGR_*), or Theil–Sen if you prefer robustness. Every forecast is just slope × days plus a starting point, and every anomaly is explained by its median and MAD — so you can check any number by hand. Nothing to train, nothing hidden.

Reaches: +30 / +90 / +180 / +365 days, with bands Needs: nothing beyond the views
Tier 2 · optional

OML ESM — exponential smoothing

One Oracle Machine Learning model per series via DBMS_DATA_MINING. CPU uses additive Winters (weekly seasonality); tablespaces default to AUTO, which trains both Holt and additive Winters as holdout twins and keeps whichever forecast the held-out days more accurately. Shown against Tier 1 in the report.

Reaches: +30 only — 19c hard-caps the horizon at 30 steps Needs: CREATE MINING MODEL
Beyond the report

It doesn't only print a report

The top view layer is a machine-readable surface, and a handful of standalone scripts cover the rest of the operational day.

CAPR_ALERTS is one row per current issue — a severity, a kind, the (dbid, con_dbid) keys plus a resolved DB/PDB label, the metric value against its threshold, and a ready-to-page message. Poll it from an OEM metric extension, Zabbix, Nagios, or a scheduler job:

SQL*Plusexample
SQL> SELECT severity, kind, db_pdb, message FROM capr_alerts ORDER BY sev_rank;

Both reports build their at-a-glance blocks from that same view, so what pages you and what the report says can never disagree.

Trust

Safe by design

Two properties make this comfortable to install on a database you care about.

i

Read-only against your data. The reports and all CAPV / CAPD / CAPF / CAPA / CAPR views only ever SELECT. The suite writes exactly three tables of its own — CAP_CONFIG (tuning knobs), CAP_TBSPC_OVERRIDE (operator-set ceilings and exclusions) and CAP_ML_MODEL (the Tier 2 registry) — and nothing else.

▸

Safe to re-run. Re-running the installer is idempotent and non-destructive: your config knobs, limit overrides and trained models all survive @install.sql. A full teardown is a single @uninstall.sql.

What isn't in it

Tablespaces, CPU, the fixed-ceiling series, anomalies, alerts and the backtest all ship today. Two items are deliberately held for v2.
