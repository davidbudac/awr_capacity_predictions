In-database · Oracle 19c floor · read-only

Capacity forecasting that lives inside the database.

SQL-level growth forecasting, pollable alerts and deterministic anomaly detection driven entirely by AWR history, with no external ML stack, no agent, no data export. Just views, three small tables of its own, an OML package, and read-only SQL*Plus reports in text and HTML.

5 view layers 9 seam views 3 persisted tables 2 forecast engines read-only against AWR safe to re-run

This suite turns the history Oracle already collects (AWR) into forward-looking capacity answers without moving a row out of the database. Five view layers: CAPV_ (seam) → CAPD_ (daily) → CAPF_ (forecast) → CAPA_ (anomaly) → CAPR_ (integration). The top layer is what the reports and any monitoring system read.

How it works, in one idea

Write the analytics once, swap the data source underneath

The whole design hangs on a single trick called the seam.

Every calculation reads a thin layer of nine CAPV_ views shaped like Oracle's AWR dictionary; nothing above them touches DBA_HIST_* directly. Swap that one install file and the identical SQL runs against live AWR, a fleet warehouse, or test fixtures whose answers are worked out in advance. How it works walks the full pipeline.

Forecasting

Two engines, side by side

An auditable baseline, and an optional seasonality-aware second opinion.

Tier 1 · always on

Pure SQL, a straight trend line

Linear regression (REGR_*), or Theil–Sen for robustness. Every forecast is slope × days plus a starting point, every anomaly is explained by its median and MAD, so you can check any number by hand. Nothing to train.

Reaches: +30 / +90 / +180 / +365 days, with bands Needs: nothing beyond the views
Tier 2 · optional

OML ESM, exponential smoothing

One Oracle Machine Learning model per series via DBMS_DATA_MINING. CPU uses additive Winters; tablespaces default to AUTO, which picks Holt or additive Winters by holdout accuracy. Shown against Tier 1 in the report.

Reaches: +30 only; 19c hard-caps the horizon at 30 steps Needs: CREATE MINING MODEL
Trust

Safe by design

Two properties, so it is comfortable to install on a database you care about.

i

Read-only against your data. The reports and all CAPV / CAPD / CAPF / CAPA / CAPR views only ever SELECT. The suite writes exactly three tables of its own, CAP_CONFIG (tuning knobs), CAP_TBSPC_OVERRIDE (operator-set ceilings and exclusions) and CAP_ML_MODEL (the Tier 2 registry), and nothing else.

▸

Safe to re-run. Re-running the installer is idempotent and non-destructive. Your config knobs, limit overrides and trained models all survive @install.sql. A full teardown is a single @uninstall.sql.
