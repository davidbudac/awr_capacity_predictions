Reference

The 19c caveats, the full knob list, every object the suite creates, how to remove them again, and the full installation reference for anything beyond the quickstart.

Thresholds live in CAP_CONFIG, and the object names are exactly what @install.sql creates. Skim the caveats first; they explain most of what surprises people. The knob table and object index below are lookups.

Verified on 19c

Caveats worth knowing

The non-obvious facts, verified on a real 19c box (19.27), that shape what you'll see.

!

AWR retention bounds everything. Default is 8 days; the 90-day training window needs more. Short retention → INSUFFICIENT_HISTORY, by design.

i

Block size comes from DBA_HIST_TABLESPACE, not the datafile view — DBA_HIST_DATAFILE has no SYSTEM row on stock 19c, which would otherwise drop that tablespace.

i

REGR_R2 returns 1 for a flat series, not NULL (NULL only when x variance is zero). So FLAT is detected by slope = 0.

!

ESM is capped at +30 days on 19c. The horizon hard-caps at 30 steps regardless of series length, so +90/+180/+365 are always REGR-only.

i

Anomalies key off the growth rate, not the raw delta. Across an AWR gap, the delta is divided by day_gap, so a multi-day gap is never mistaken for a one-day spike.

i

Container identity is the composite key. Analytics key on (dbid, con_dbid); con_dbid separates PDBs whose TS# collide. Cross-DBID series stitching is a v2 item, as is memory (SGA / PGA) forecasting.

▸

Re-install is non-destructive. Your CAP_CONFIG knobs, CAP_TBSPC_OVERRIDE rows and CAP_ML_MODEL registry survive @install.sql. Use @uninstall.sql for a full teardown.

Tuning

Configuration knobs

Every threshold lives in CAP_CONFIG. The views read it only through the one-row view CAP_CFG, which has one column per knob, named after the knob. Tuning never means editing SQL.

SQL*Plusexample
SQL> UPDATE cap_config SET cfg_value = 0.70 WHERE cfg_name = 'r2_gate';
SQL> SELECT * FROM cap_config ORDER BY cfg_name;   -- the full annotated list
SQL> SELECT * FROM cap_cfg_check WHERE status <> 'OK';   -- missing or out-of-range knobs
SQL> UPDATE cap_config SET cfg_value = cfg_default WHERE cfg_name = 'r2_gate';   -- back to the shipped value
!

Reset a knob, never delete it. A deleted row reads as NULL in CAP_CFG, and a NULL knob makes the views return no rows or no flags without an error. cfg_default holds the shipped value and is refreshed on every install, so UPDATE cap_config SET cfg_value = cfg_default is the reset. Re-running @install.sql never touches cfg_value; it re-inserts a deleted key with its shipped value.

CAP_CFG_CHECK returns one row per knob with its value and a status: OK, MISSING (no CAP_CONFIG row) or BAD (a broken rule: recent_days ≤ train_days, min_train_days ≥ 14, dtf_crit ≤ dtf_warn, nearfull_warn_pct ≤ nearfull_crit_pct, trailing_min_hist ≤ mad_window_days, weekly_min_hist ≤ dow_weeks, hour_gap_ratio > 0, each alert_modes_* a whole number 0 to 7, shift_days ≤ shift_baseline_days, esm_prediction_step between 1 and 30, slope_method in 0/1/2, esm_tbspc_model in 0/1/2, esm_max_age_days ≥ 0, esm_auto_tie_pct ≥ 0, complete_day_pct between 1 and 100, stale_days ≥ 0, cyclic_min_cliffs 0 or a whole number ≥ 2, cpu_quality_gate and cpu_deseason in 0/1). A rule between two knobs is reported on the first one. The reason column says what to fix.

accel_slope_floor_bpd1,048,576Minimum |slope| (bytes/day, 1 MiB) before accel_ratio is computed; below it a near-flat series would divide by ~0 and report an absurd acceleration, so the ratio is NULL.
slope_method0M9.2 slope estimator for the CAPF_* fits. CAP_CONFIG is numeric, so the encoding is 0 = OLS (REGR_SLOPE, the default), 1 = THEILSEN (median of the pairwise slopes, robust to a one-off step) and 2 = DRIFT (median of the day-over-day rates, slope CI t·sd/√n, bands t·(sd·√h + h·se), quality OK only when the CI excludes 0). Theil-Sen is computed only under 1, so ts_slope_bpd is NULL otherwise; ols_slope_bpd, drift_slope_bpd and drift_sd_bpd are always there, and the slope_method column says which one the row used. CAPF_SERIES_FORECAST knows 0 and 2; CAPF_BACKTEST's REGR replay follows all three.
cyclic_min_cliffs2A tablespace with at least this many shrink cliffs (the reset_on_shrink rule) in its train_days window is graded CYCLIC: no reset, judged on its peaks (cycle_days, cycle_peak_pct, peak_slope_bpd, and days_to_full along the peak line). 0 turns the grade off; 1 is rejected (one cliff is a purge, and the reset handles it).
cpu_quality_gate1CAPF_CPU_TREND quality: 1 = OK when |slope| > slope_ci_per_day (slope significance), 0 = the legacy R² ≥ r2_gate. slope_sig reports the significance test either way.
cpu_deseason1CAPF_CPU_TREND: 1 = subtract the weekday / weekend mean of the window (and add back the window mean) before the fit, so a weekly pattern drops out and a trend can reach OK; 0 = fit the raw daily values. Both CPU knobs at 0 reproduce the fit before they existed.
stale_days3A CAPF_* series whose last_day is more than this many days before newest_day (the newest day of its daily source for the same dbid) reads is_current = 'N': a dropped tablespace, a retired DBID, a series that stopped arriving. Data-driven, no SYSDATE.
reset_on_shrink1M9.3: 1 = restart a tablespace's training window at the most recent large negative used_bytes step, so a post-purge series is not fitted across the cliff (train_start / reset_day); 0 = fit straight through it.
shrink_mad_k6M9.3 threshold: a daily delta below −GREATEST(k·MAD_σ of the window's deltas, abs_floor_bytes) is a shrink change-point. Higher than mad_k (3) on purpose — this restarts a fit, so it should only fire on real cliffs.
cpu_sat_pct80CPU busy percent treated as saturated for days-to-saturation.
peak_hour_from8Peak window start (hour, exclusive): an interval is "peak" when its end hour is in (from, to].
peak_hour_to18Peak window end (hour, inclusive). Drives BUSY_PEAK / db_cpu_peak_pct.
cpu_sat_on_p9511 = CPU_SAT alerts key off the BUSY_P95 busy-hour trend; 0 = the daily-average BUSY_PCT trend.
series_sat_pct90M11: percent of a fixed-ceiling series' limit (PROCESSES, SESSIONS, DB_SIZE_GB) treated as saturated, since hitting processes exactly is an outage. Drives CAPF_SERIES_FORECAST.days_to_limit and the SERIES_LIMIT alert.
abs_floor_bytes104,857,600Threshold floor (100 MiB/day) for tablespace growth-rate anomalies, in every mode; guards flat baselines (MAD = 0).
dow_weeks8Weeks of history (ts − 7k, k = 1..dow_weeks) forming the SAME_DOW and HOUR_OF_WEEK anomaly baselines.
dtf_warn90days_to_full at/below this = WARN in the report.
dtf_crit30days_to_full at/below this = CRIT in the report.
nearfull_warn_pct90Percent-used at/above which a tablespace raises a near-full-now WARN, whatever the forecast quality.
nearfull_crit_pct97Percent-used at/above which a tablespace raises a near-full-now CRIT, whatever the forecast quality.
trailing_min_hist7M15: minimum baseline observations before a TRAILING anomaly can flag, any series. Replaces tbspc_min_hist; an install carries an operator's value over and deletes the old key.
weekly_min_hist3M15: minimum baseline observations before a SAME_DOW or HOUR_OF_WEEK anomaly can flag. Replaces cpu_min_dow_hist, carried over the same way.
cpu_min_mad_pct3Floor (whole percent) on CPU day MAD_σ, so an exactly-flat baseline still flags a real jump: the threshold is at least mad_k × 3 = 9 points.
cpu_min_mad_pct_hour5M15: the same floor for hour-grain CPU (HOUR_OF_WEEK), higher because hourly values are noisier than daily averages: a 15-point threshold at least.
series_floor_count10M15: anomaly threshold floor for the COUNT series (PROCESSES, SESSIONS), in processes or sessions.
series_floor_gib0.5M15: anomaly threshold floor (GiB/day) for the GIB_PER_DAY series: the REDO_GB_DAY level and DB_SIZE_GB growth.
hour_gap_ratio1.5M15: at hour grain an interval of 0 h or less, or longer than LEAST(cpu_gap_hours, hour_gap_ratio × the instance's median interval), is a gap: its hour is neither scored nor used as a baseline. Must be > 0.
alert_modes_tbspc1M15 bitmask of the baseline modes that raise TBSPC_ANOM: 1 = TRAILING, 2 = SAME_DOW, 4 = HOUR_OF_WEEK (no effect here: tablespaces are day grain only); add them, 0 = none. Every mode is scored either way; this decides only what pages. It also picks the headline mode of the 1:1 point feeds (the lowest day bit set).
alert_modes_cpu2M15 bitmask for CPU_ANOM and DBCPU_ANOM, same encoding. 6 pages on both weekly modes; an HOUR_OF_WEEK day raises one row carrying its worst hour.
alert_modes_series1M15 bitmask for SERIES_ANOM, same encoding (4 has no effect: day grain only).
cpu_gap_hours12M10.5: a snapshot interval longer than this many hours is an AWR gap / downtime. Its day gets gap_flag = 'Y', is skipped by the CPU anomaly and level-shift baselines, and is left out of busy_p95 / busy_max / the peak window. Half a day is deliberately loose: the flag suppresses scoring, so a tighter default would silence the CPU anomaly layer wherever snapshot intervals are wide.
complete_day_pct80Percent of a day (86400 s) of valid counter intervals a CAPD_CPU_DAILY / CAPD_DBTIME_DAILY / REDO_GB_DAY day needs for is_complete = 'Y'. The first day of history, today, and restart or outage days fall below it; gap_flag does not catch those.
shift_days7M10.3: length of the recent window whose median CAPA_CPU_SHIFT compares against the baseline — and the N of the N-of-M confirmation.
shift_baseline_days28M10.3: length of the baseline window immediately before the recent window.
shift_min_pct15M10.3: minimum |recent median − baseline median|, in percentage points, before a level shift is flagged.
esm_prediction_step30OML ESM forecast horizon in steps (days). Oracle 19c hard-caps this at 30.
esm_tbspc_model2ESM model type for tablespaces: 0 = EXSM_HOLT, 1 = EXSM_ADDWINTERS with a 7-day season, 2 = AUTO — train both as holdout twins and keep the lower-MAPE one (ties → Holt).
esm_select_by_backtest1Enables the AUTO comparison (two extra models per tablespace, per retrain). 0 makes AUTO fall back to EXSM_HOLT and trains no candidate twins.
backtest_holdout_days28Holdout window (days) CAPF_BACKTEST fits before and scores against. Keep it at or below 30 so ESM can cover it on 19c.
esm_max_age_days7Tier 2: an ESM model trained more than this many days before its series' last day is stale; CAPF_COMPARE drops it.
esm_auto_tie_pct0.25Tier 2 AUTO: candidate MAPEs closer than this many percentage points tie and EXSM_HOLT is kept (chosen_by = AUTO_TIE).
suite_version15Not a tuning knob. The suite release (latest PLAN.md milestone) that built the objects; every install overwrites it and doctor.sql prints it. No analytic view reads it; CAP_CFG_CHECK reports it BAD below 15.

That's the complete shipped set: 48 knobs plus suite_version, the 49 rows ddl/05_config.sql seeds. SELECT * FROM cap_config ORDER BY cfg_name prints the same knobs with their annotations straight from the database, including any values you've since overridden. Where cfg_value differs from cfg_default, the knob has been tuned.

Teardown

Two scripts, plus a package call if you trained the Tier 2 models.

SQL*Plusyou run
SQL> @test/fixture_remove.sql   -- fixture mode only: drop CAP_FIXTURE_* tables
SQL> @uninstall.sql             -- drop all CAP_* / CAPV_ / CAPD_ / CAPF_ / CAPA_ / CAPR_ objects
SQL> EXEC cap_forecast_ml.drop_all;  -- (if trained) remove the OML models
▸

@install.sql is non-destructive. Re-running it preserves your tuning and trained models. @uninstall.sql is the full teardown — it drops every CAP_* / CAPV_ / CAPD_ / CAPF_ / CAPA_ object.

Show the full installation reference

There is nothing to download beyond this repository and no external runtime to stand up. You pick a seam_mode, connect where that mode's data lives, and run @install.sql. It builds every CAP* object and verifies it compiled. Run @doctor.sql first and it will tell you, before you install anything, whether this database can actually produce forecasts. This page is the generic, portable procedure; for the step-by-step walkthrough on the author's 19c test box, see Testing.

Production path

A dedicated owner: create_owner.sql

The quickstart installs into SYS. That is fine for a first look, but it puts every CAP* object in the dictionary schema. install.sql prints the target schema and warns when it is SYS.

sqlplus · CDB$ROOTyou run, once
sqlplus / as sysdba
SQL> DEFINE owner = C##AWRCAP          -- optional; this is the CDB default
SQL> @create_owner.sql

create_owner.sql is not part of the quickstart. Run it once as SYSDBA. In CDB$ROOT it creates the common user C##AWRCAP and grants with CONTAINER=ALL; in a non-CDB or a PDB it creates the local user AWRCAP. It grants, all directly: the privileges in the table above plus CREATE SESSION, a quota (owner_quota, default 1G, on owner_ts, default the database default tablespace), SELECT on the ten DBA_HIST_* views ddl/10_seam_local.sql reads, and SELECT on DBA_HIST_WR_CONTROL and V_$PARAMETER, which only doctor.sql reads. Without DEFINE owner_pw the user has no password (NO AUTHENTICATION), so you install as SYSDBA with ALTER SESSION SET CURRENT_SCHEMA = C##AWRCAP, or set a password later. Re-running it is safe: an existing user is kept and the grants are re-applied. It prints every statement and exits non-zero if one failed.

@@

Always run from the repo root. SQL*Plus resolves @@ includes relative to the outermost caller on 19c, so install.sql and report/report.sql must be launched from the top of the repository (they reference their pieces as @@ddl/… / @@report/…). Start elsewhere and the includes won't resolve.

Preflight

Run doctor.sql first

One page that answers "will this suite actually produce forecasts for me, and if not, why not?", before you install and again afterwards.

sqlplus · where you intend to installyou run
SQL> @doctor.sql

doctor.sql is a standalone script at the repo root and is not part of install.sql. It is strictly read-only: it creates nothing, drops nothing, writes nothing. It only SELECTs from the data dictionary and prints a PASS / WARN / FAIL checklist through DBMS_OUTPUT. Every probe is exception-wrapped inside one anonymous block, so a missing object or a missing grant prints a single WARN line instead of aborting the run. The seam

Three modes

One idea makes install portable: all analytics read from the nine CAPV_ seam views (plus the CAPV_CONTRACT diagnostic), and seam_mode chooses what they point at.

seam_mode — what it points at, and where to install it
seam_modeSourceInstall asNotes
local DBA_HIST_* The create_owner.sql owner in CDB$ROOT (or sysdba, which installs into SYS) Needs the Diagnostics Pack + direct SELECT grants on the DBA_HIST views.
warehouse AWRV_* seam views Warehouse owner (AWRWH), or a schema with SELECT on the AWRV_* views Presents every collected database, keyed on (dbid, con_dbid). One gap; see below.
fixture CAP_FIXTURE_* Any schema with CREATE privileges Test hook: run test/fixture_install.sql first (see Testing).

An unrecognised seam_mode is not silently ignored: the installer forces a ZERO_DIVIDE so it aborts loudly instead of skipping the seam. The value is case-insensitive, and defaults to local if it resolves to nothing.

Install

Warehouse mode

Point the seam at a central fleet collector instead of this database's own AWR. Same code, reporting across many databases at once.

Install where the AWRV_* views are visible: as the warehouse owner (AWRWH), or a schema with direct SELECT on them. ddl/11_seam_warehouse.sql re-maps the CAPV_ views onto those AWRV_* views, so warehouse mode is byte-identical downstream to local mode: same math, same report. The warehouse presents every collected database (one target reads as one DB, many targets as a fleet report), and every row carries its con_dbid so containers never collide.

sqlplus · AWRWHyou run
-- connected as the warehouse owner (or a schema with SELECT on AWRV_*)
SQL> DEFINE seam_mode = 'warehouse'
SQL> @install.sql
!

One gap: CAPV_RESOURCE_LIMIT is a stub in warehouse mode. The awr-fleet-warehouse collector does not gather DBA_HIST_RESOURCE_LIMIT yet, so there is no awrv_resource_limit view to map onto. Rather than leave the object missing, which would make CAPD_SERIES_DAILY and everything above it INVALID, the warehouse seam emits the exact column contract with WHERE 1 = 0, i.e. zero rows. The practical effect: the PROCESSES and SESSIONS series simply do not appear for warehouse-mode databases. REDO_GB_DAY and DB_SIZE_GB work normally, as does everything else. Closing the gap is tracked as a TODO on M11.1 in PLAN.md.

Opt-in

Scheduler jobs

A second standalone script, also outside install.sql. Both jobs it creates land DISABLED. Nothing runs until you say so.

SQL> @install_jobs.sql

-- they arrive disabled; turn on whichever you want
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_ML_RETRAIN')
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_REPORT_SPOOL_JOB')

SQL> @uninstall_jobs.sql             -- drops both jobs + the procedure

ObjectScheduleDoes
CAP_ML_RETRAIN
job		 FREQ=WEEKLY, Sun 02:00 Calls cap_forecast_ml.train_all so the Tier 2 OML ESM models track the latest AWR days. Needs CREATE MINING MODEL.

procedure		 on demand Writes <dir>/cap_alerts.txt through UTL_FILE: a header (timestamp, database, CRIT/WARN/INFO counts) then one pipe-delimited line per CAPR_ALERTS row. Callable by hand: EXEC cap_report_spool('CAP_REPORTS').

You must create the directory object yourself. That needs CREATE ANY DIRECTORY and a path decision only you can make, so the script refuses to guess: it checks ALL_DIRECTORIES and, if &report_dir (default CAP_REPORTS) is missing, prints the exact DDL to run: CREATE OR REPLACE DIRECTORY … AS '…' plus GRANT READ, WRITE ON DIRECTORY … TO <schema>. i

The spool job is not "the report". SQL*Plus spooling cannot happen inside a scheduler job, since there is no SQL*Plus there, so what the job writes is a pollable alert snapshot, not the formatted capacity report. For the full report, keep driving report/report.sql from cron or your OS scheduler. Re-running install_jobs.sql is idempotent: it drops both jobs if present, then recreates them, again disabled.

Re-running it · upgrading

Idempotent, non-destructive re-install

Re-running the installer is safe: it rebuilds the views but never wipes what you've tuned, overridden or trained.

▸

Your knobs, overrides and models survive. Re-running @install.sql preserves all three persisted tables: the CAP_CONFIG knobs, your CAP_TBSPC_OVERRIDE rows and the CAP_ML_MODEL registry (with its OML models). The 00_drop step deliberately leaves those tables alone, and the config MERGE inserts keys that are missing and on existing keys refreshes only cfg_default and cfg_desc, so it never overwrites a value you changed. The one exception is suite_version, which is not a knob: the same MERGE overwrites its value on every install so doctor.sql shows which release built the objects.

Upgrading is the same command. Pull the new revision and re-run @install.sql with the same seam_mode: every view is CREATE OR REPLACE, both tables are created only if absent, and any knob a new milestone added is MERGE-seeded with its shipped default while your existing values stay exactly as you set them. To reset one knob to its shipped default, UPDATE cap_config SET cfg_value = cfg_default for that row. Run @doctor.sql afterwards to confirm nothing came out INVALID. For a full teardown of the opt-in scheduler jobs, views, types, package, OML models and all three tables, use @uninstall.sql. It prints any error other than "does not exist" and ends with the number of CAP% objects left in the schema (0 expected).

The one caveat that bites

AWR retention bounds everything

Forecasts are only as long as the history behind them, and stock retention is short.

!

Default retention is only 8 days. That's far below the 90-day training window, so on a stock box local-mode forecasts degrade to INSUFFICIENT_HISTORY (TRAIN_N < min_train_days) and say so loudly. That is correct behaviour, not a bug. The report refuses to project a trend it can't yet see. doctor.sql checks 5 to 7 tell you this before you install.

To get real trends, raise AWR retention (here, to 90 days, expressed in minutes):

sqlplus · CDB$ROOTyou run
SQL> EXEC DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS(retention => 90*24*60);
i

This one is a real change to Oracle. Unlike everything else in this suite, which only ever SELECTs, MODIFY_SNAPSHOT_SETTINGS is a persistent AWR configuration change. It also only affects future snapshots: past history is not backfilled, so the training window fills in from the day you raise retention forward.

With that done, head to Usage to run the report and read its eight sections, or prove every part against known answers with the fixture self-check on Testing first.
