Reference

The non-obvious facts, the full knob list, every object the suite creates, and clean teardown — the details you reach for once you know what the tool does.

Everything here traces to a single source of truth. Thresholds live in CAP_CONFIG, the object names are exactly what @install.sql creates, and each caveat was verified on a real 19c box. Skim the caveats first — they explain most of what surprises people — then use the knob table and object index as a lookup.

Verified on 19c

Caveats worth knowing

The non-obvious facts, verified on a real 19c box (19.27), that shape what you'll see.

!

AWR retention bounds everything. Default is 8 days; the 90-day training window needs more. Short retention → INSUFFICIENT_HISTORY, by design.

i

Block size comes from DBA_HIST_TABLESPACE, not the datafile view — DBA_HIST_DATAFILE has no SYSTEM row on stock 19c, which would otherwise drop that tablespace.

i

REGR_R2 returns 1 for a flat series, not NULL (NULL only when x variance is zero). So FLAT is detected by slope = 0.

!

ESM is capped at +30 days on 19c. The horizon hard-caps at 30 steps regardless of series length, so +90/+180/+365 are always REGR-only.

i

Anomalies key off the growth rate, not the raw delta. Across an AWR gap, the delta is divided by day_gap, so a multi-day gap is never mistaken for a one-day spike.

i

Container identity is the composite key. Analytics key on (dbid, con_dbid); con_dbid separates PDBs whose TS# collide. Cross-DBID series stitching is a v2 item.

▸

Re-install is non-destructive. Your CAP_CONFIG knobs, CAP_TBSPC_OVERRIDE rows and CAP_ML_MODEL registry survive @install.sql. Use @uninstall.sql for a full teardown.

Tuning

Configuration knobs

Every threshold lives in CAP_CONFIG, read by the views through a one-row cfg CTE. Tuning never means editing SQL.

SQL*Plusexample
SQL> UPDATE cap_config SET cfg_value = 0.70 WHERE cfg_name = 'r2_gate';
SQL> SELECT * FROM cap_config ORDER BY cfg_name;   -- the full annotated list

min_train_days14Minimum REGR_COUNT before a forecast is trusted; below this → INSUFFICIENT_HISTORY.
r2_gate0.60REGR_R2 below this marks a forecast LOW_CONFIDENCE.
mad_k3MAD multiplier k: |value − median| > k·MAD_σ flags an anomaly.
mad_window_days28Trailing window length for the rolling median / MAD baseline (days).
anomaly_report_days14Trailing-days window of anomalies CAPR_ALERTS raises. Not the same window as the report's own anomaly_days presentation knob (sections 3 and 5, default 30) — this one bounds the pollable alert view.
report_min_gb1Report sections 2 and 6a print a tablespace only if it is growing, near-full, or at least this many GiB used (is_reportable), then cap at top_n by rank_report.
accel_slope_floor_bpd1,048,576Minimum |slope| (bytes/day, 1 MiB) before accel_ratio is computed; below it a near-flat series would divide by ~0 and report an absurd acceleration, so the ratio is NULL.
slope_method0M9.2 slope estimator for the CAPF_* fits. CAP_CONFIG is numeric, so the encoding is 0 = OLS (REGR_SLOPE, the default) and 1 = THEILSEN (median of the pairwise slopes, robust to a one-off step). Both are always exposed as ols_slope_bpd / ts_slope_bpd; the slope_method column says which one the row used.
reset_on_shrink1M9.3: 1 = restart a tablespace's training window at the most recent large negative used_bytes step, so a post-purge series is not fitted across the cliff (train_start / reset_day); 0 = fit straight through it.
shrink_mad_k6M9.3 threshold: a daily delta below −GREATEST(k·MAD_σ of the window's deltas, abs_floor_bytes) is a shrink change-point. Higher than mad_k (3) on purpose — this restarts a fit, so it should only fire on real cliffs.
cpu_sat_pct80CPU busy percent treated as saturated for days-to-saturation.
peak_hour_from8Peak window start (hour, exclusive): an interval is "peak" when its end hour is in (from, to].
peak_hour_to18Peak window end (hour, inclusive). Drives BUSY_PEAK / db_cpu_peak_pct.
cpu_sat_on_p9511 = CPU_SAT alerts key off the BUSY_P95 busy-hour trend; 0 = the daily-average BUSY_PCT trend.
series_sat_pct90M11: percent of a fixed-ceiling series' limit (PROCESSES, SESSIONS, DB_SIZE_GB) treated as saturated, since hitting processes exactly is an outage. Drives CAPF_SERIES_FORECAST.days_to_limit and the SERIES_LIMIT alert.
abs_floor_bytes104,857,600Absolute floor (100 MiB) for the tablespace-delta anomaly threshold; guards flat baselines (MAD = 0).
dow_weeks8Number of prior same-weekday observations forming the CPU seasonal baseline.
dtf_warn90days_to_full at/below this = WARN in the report.
dtf_crit30days_to_full at/below this = CRIT in the report.
tbspc_min_hist7Minimum trailing observations before a tablespace anomaly can flag.
cpu_min_mad_pct3Floor (whole percent) on CPU MAD_σ so an exactly-flat seasonal baseline still flags a real jump.
cpu_min_dow_hist3Minimum prior same-weekday observations before a CPU anomaly can flag.
cpu_gap_hours12M10.5: a snapshot interval longer than this many hours is an AWR gap / downtime. Its day gets gap_flag = 'Y', is skipped by the CPU anomaly and level-shift baselines, and is left out of busy_p95 / busy_max / the peak window. Half a day is deliberately loose: the flag suppresses scoring, so a tighter default would silence the CPU anomaly layer wherever snapshot intervals are wide.
shift_days7M10.3: length of the recent window whose median CAPA_CPU_SHIFT compares against the baseline — and the N of the N-of-M confirmation.
shift_baseline_days28M10.3: length of the baseline window immediately before the recent window.
shift_min_pct15M10.3: minimum |recent median − baseline median|, in percentage points, before a level shift is flagged.
esm_prediction_step30OML ESM forecast horizon in steps (days). Oracle 19c hard-caps this at 30.
esm_tbspc_model2ESM model type for tablespaces: 0 = EXSM_HOLT, 1 = EXSM_ADDWINTERS with a 7-day season, 2 = AUTO — train both as holdout twins and keep the lower-MAPE one (ties → Holt).
esm_select_by_backtest1Enables the AUTO comparison (two extra models per tablespace, per retrain). 0 makes AUTO fall back to EXSM_HOLT and trains no candidate twins.

That's the complete shipped set. SELECT * FROM cap_config ORDER BY cfg_name prints the same knobs with their annotations straight from the database, including any values you've since overridden.

Clean removal

Teardown

Clean removal of everything the suite created.

SQL*Plusyou run
SQL> @test/fixture_remove.sql   -- fixture mode only: drop CAP_FIXTURE_* tables
SQL> @uninstall.sql             -- drop all CAP_* / CAPV_ / CAPD_ / CAPF_ / CAPA_ / CAPR_ objects
SQL> EXEC cap_forecast_ml.drop_all;  -- (if trained) remove the OML models
▸

@install.sql is non-destructive. Re-running it preserves your tuning and trained models. @uninstall.sql is the full teardown — it drops every CAP_* / CAPV_ / CAPD_ / CAPF_ / CAPA_ object.
