Installation

Install it where the data source is visible, run the layered DDL, and you're done in minutes. The installer is idempotent and non-destructive — safe to re-run against a database you care about.

There is nothing to download beyond this repository and no external runtime to stand up. You pick a seam_mode, connect where that mode's data lives, and run @install.sql — it builds every CAP* object and verifies it compiled. This page is the generic, portable procedure; for the step-by-step walkthrough on the author's 19c test box, see Testing.

Before you start

Prerequisites

A short list, and most of it only applies to local mode against live AWR.

What each mode needs
PrerequisiteNeeded forDetail
Oracle Database 19c all modes 19c is the floor. The suite uses no 21c/23c syntax (notably no standalone WINDOW clause — every window call is inline OVER (PARTITION BY … ORDER BY …)), so it installs unchanged on 19c and up.
Diagnostics Pack local mode DBA_HIST_* is Diagnostics Pack territory. Check CONTROL_MANAGEMENT_PACK_ACCESS is DIAGNOSTIC+TUNING before installing local mode.
Direct SELECT on DBA_HIST_* local mode Granted directly, not via a role — view compilation ignores role-granted privileges, so the CAPV_ seam views won't compile without direct grants on the underlying DBA_HIST_* views.
CREATE MINING MODEL Tier 2 (optional) Only for the OML ESM engine. Free in all editions since Dec 2019. Tier 1 (pure-SQL REGR_*) needs nothing beyond the views.
Run from the repo root all modes install.sql and report/report.sql use relative @@ includes — launch them from the repository root.
@@

Always run from the repo root. SQL*Plus resolves @@ includes relative to the outermost caller on 19c, so install.sql and report/report.sql must be launched from the top of the repository (they reference their pieces as @@ddl/… / @@report/…). Start elsewhere and the includes won't resolve.

The seam

Three modes

One idea makes install portable: all analytics read from the six CAPV_ seam views, and seam_mode chooses what they point at.

seam_mode — what it points at, and where to install it
seam_modeSourceInstall asNotes
local DBA_HIST_* sysdba in CDB$ROOT Needs the Diagnostics Pack + direct SELECT grants on the DBA_HIST views.
warehouse AWRV_* seam views Warehouse owner (AWRWH), or a schema with SELECT on the AWRV_* views Presents every collected database, keyed on (dbid, con_dbid).
fixture CAP_FIXTURE_* Any schema with CREATE privileges Test hook — run test/fixture_install.sql first (see Testing).
Install

Local mode

The common case: point the seam at this database's live AWR. Connect as sysdba in CDB$ROOT — that's where AWR lives — define the mode, and run the installer.

sqlplus · CDB$ROOTyou run
sqlplus / as sysdba          -- lands in CDB$ROOT, where AWR lives
SQL> DEFINE seam_mode = 'local'
SQL> @install.sql

install.sql runs the layered DDL in order — 00_drop → 05_config → seam → 20_daily → 30_forecast → 40_anomaly → 50_ml — and ends with a validity check that fails loudly if any CAP* object came out invalid.

Install

Warehouse mode

Point the seam at a central fleet collector instead of this database's own AWR — the same code, reporting across many databases at once.

Install where the AWRV_* views are visible: as the warehouse owner (AWRWH), or a schema with direct SELECT on them. ddl/11_seam_warehouse.sql re-maps the CAPV_ views onto those AWRV_* views, so warehouse mode is byte-identical downstream to local mode — same math, same report. The warehouse presents every collected database (one target reads as one DB, many targets as a fleet report), and every row carries its con_dbid so containers never collide.

sqlplus · AWRWHyou run
-- connected as the warehouse owner (or a schema with SELECT on AWRV_*)
SQL> DEFINE seam_mode = 'warehouse'
SQL> @install.sql
Re-running it

Idempotent, non-destructive re-install

Re-running the installer is safe: it rebuilds the views but never wipes what you've tuned or trained.

▸

Your overrides and models survive. Re-running @install.sql preserves both persisted tables — CAP_CONFIG overrides and the CAP_ML_MODEL registry (and its OML models). The 00_drop step deliberately leaves those two tables alone, and the config MERGE only seeds keys that are missing, so it never overwrites a value you changed. For a full teardown, use @uninstall.sql.

The one caveat that bites

AWR retention bounds everything

Forecasts are only as long as the history behind them — and stock retention is short.

!

Default retention is only 8 days. That's far below the 90-day training window, so on a stock box local-mode forecasts degrade to INSUFFICIENT_HISTORY (TRAIN_N < min_train_days) and say so loudly. That is correct behaviour, not a bug — the report refuses to project a trend it can't yet see.

To get real trends, raise AWR retention (here, to 90 days, expressed in minutes):

sqlplus · CDB$ROOTyou run
SQL> EXEC DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS(retention => 90*24*60);
i

This one is a real change to Oracle. Unlike everything else in this suite — which only ever SELECTs — MODIFY_SNAPSHOT_SETTINGS is a persistent AWR configuration change. It also only affects future snapshots: past history is not backfilled, so the training window fills in from the day you raise retention forward.

With that done, head to Usage to run the report and read its six sections — or prove every part against known answers with the fixture self-check on Testing first.
