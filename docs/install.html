Guide

Installation

Run the preflight, install it where the data source is visible, run the layered DDL, and you're done in minutes. The installer is idempotent and non-destructive — safe to re-run against a database you care about.

There is nothing to download beyond this repository and no external runtime to stand up. You pick a seam_mode, connect where that mode's data lives, and run @install.sql — it builds every CAP* object and verifies it compiled. Run @doctor.sql first and it will tell you, before you install anything, whether this database can actually produce forecasts. This page is the generic, portable procedure; for the step-by-step walkthrough on the author's 19c test box, see Testing.

Before you start

Prerequisites

A short list, and most of it only applies to local mode against live AWR.

What each mode needs
PrerequisiteNeeded forDetail
Oracle Database 19c all modes 19c is the floor. The suite uses no 21c/23c syntax (notably no standalone WINDOW clause — every window call is inline OVER (PARTITION BY … ORDER BY …)), so it installs unchanged on 19c and up.

Preflight

Run doctor.sql first

One page that answers "will this suite actually produce forecasts for me, and if not, why not?" — before you install, and again afterwards.

sqlplus · where you intend to installyou run
SQL> @doctor.sql

doctor.sql is a standalone script at the repo root and is not part of install.sql. It is strictly read-only: it creates nothing, drops nothing, writes nothing — it only SELECTs from the data dictionary and prints a PASS / WARN / FAIL checklist through DBMS_OUTPUT. Every probe is exception-wrapped inside one anonymous block, so a missing object or a missing grant prints a single WARN line instead of aborting the run. Run it in the schema and container you intend to install into.

What the checklist covers
#CheckWhat it tells you
1Diagnostics PackCONTROL_MANAGEMENT_PACK_ACCESS includes DIAGNOSTIC. If not, AWR collects nothing to fit and forecasts will be empty.
2DBA_HIST_* readableEach of the eight views the local seam needs, probed one at a time (direct grant, not via a role): snapshot, tablespace usage / tablespace / datafile, OSSTAT, sys time model, PDB instance, database instance.
3Install privilegesCREATE TABLE / VIEW / PROCEDURE / TYPE / MINING MODEL / JOB in the session user's SESSION_PRIVS.
4AWR retention & intervalFrom DBA_HIST_WR_CONTROL, per dbid — the knob that decides whether a 90-day training window can ever fill.
5History per sourceHow many distinct days each source actually holds, compared against min_train_days (read from CAP_CONFIG when the suite is installed, else the built-in 14).
6Install stateWhether CAP_CONFIG exists in this schema, any CAP* objects that are INVALID, and the seam mode in use — inferred from what CAPV_SNAPSHOT actually depends on.
▸

It ends by explaining itself. The summary counts PASS/WARN/FAIL and then spells out, in plain English, why forecasts would come back INSUFFICIENT_HISTORY — how many sources hold fewer than min_train_days distinct days, and whether retention caps history below the training window so it never can. In warehouse or fixture mode it also says that checks 2 and 5 don't apply to that install.

The seam

Three modes

One idea makes install portable: all analytics read from the nine CAPV_ seam views, and seam_mode chooses what they point at.

seam_mode — what it points at, and where to install it
seam_modeSourceInstall asNotes
local DBA_HIST_* sysdba in CDB$ROOT Needs the Diagnostics Pack + direct SELECT grants on the DBA_HIST views.
warehouse AWRV_* seam views Warehouse owner (AWRWH), or a schema with SELECT on the AWRV_* views Presents every collected database, keyed on (dbid, con_dbid). One gap — see below.
fixture CAP_FIXTURE_* Any schema with CREATE privileges Test hook — run test/fixture_install.sql first (see Testing).

An unrecognised seam_mode is not silently ignored: the installer forces a ZERO_DIVIDE so it aborts loudly instead of skipping the seam. The value is case-insensitive, and defaults to local if it resolves to nothing.

Install

Local mode

The common case: point the seam at this database's live AWR. Connect as sysdba in CDB$ROOT — that's where AWR lives — define the mode, and run the installer.

sqlplus · CDB$ROOTyou run
sqlplus / as sysdba          -- lands in CDB$ROOT, where AWR lives
SQL> DEFINE seam_mode = 'local'
SQL> @install.sql

The installer runs eleven DDL steps in dependency order and ends with a validity check that fails loudly if any CAP* object came out invalid — with a hint naming the likely cause for your seam mode.

What runs, in what order

The load order

Each step depends only on the ones above it, which is why the order is fixed and why a re-install can rebuild everything with CREATE OR REPLACE.

Steps 45 and 55 are why the two reports can't disagree. Every derived number, display label, severity marker and unit conversion is computed once in a CAPR_ view. report/report.sql and report/report_html.sql only format those rows, so the text and HTML reports read the same data by construction.

The only rows it writes

Three persisted tables

Everything else the suite creates is a view, a type or a package. These three hold state — and two of the three hold your state.

What persists, and what removes it
TableHoldsCreated bySurvives
CAP_CONFIG Every tuning knob, name/value, read by the views through a one-row cfg CTE. ddl/05_config.sql — idempotent CREATE (ORA-00955 swallowed) plus an INSERT-only MERGE. @install.sql. Dropped by @uninstall.sql.
CAP_TBSPC_OVERRIDE Operator-set tablespace ceilings and exclusions — the real storage limit when the AWR autoextend maxsize is fiction, and a Y flag for tablespaces that are supposed to fill up. The bottom of ddl/05_config.sql, same idempotent pattern. Applied once, in CAPD_TBSPC_DAILY. @install.sql — ddl/00_drop.sql does not touch it. Dropped only by @uninstall.sql.
CAP_ML_MODEL The Tier 2 registry: which OML model backs which series, and its status. ddl/50_ml.sql, idempotently. @install.sql. Dropping it would orphan the OML models, since drop_all needs the registry to find them.

See Usage for how to write CAP_TBSPC_OVERRIDE rows, and Reference for the full annotated knob list.

Install

Warehouse mode

Point the seam at a central fleet collector instead of this database's own AWR — the same code, reporting across many databases at once.

Install where the AWRV_* views are visible: as the warehouse owner (AWRWH), or a schema with direct SELECT on them. ddl/11_seam_warehouse.sql re-maps the CAPV_ views onto those AWRV_* views, so warehouse mode is byte-identical downstream to local mode — same math, same report. The warehouse presents every collected database (one target reads as one DB, many targets as a fleet report), and every row carries its con_dbid so containers never collide.

sqlplus · AWRWHyou run
-- connected as the warehouse owner (or a schema with SELECT on AWRV_*)
SQL> DEFINE seam_mode = 'warehouse'
SQL> @install.sql
!

One gap: CAPV_RESOURCE_LIMIT is a stub in warehouse mode. The awr-fleet-warehouse collector does not gather DBA_HIST_RESOURCE_LIMIT yet, so there is no awrv_resource_limit view to map onto. Rather than leave the object missing — which would make CAPD_SERIES_DAILY and everything above it INVALID — the warehouse seam emits the exact column contract with WHERE 1 = 0, i.e. zero rows. The practical effect: the PROCESSES and SESSIONS series simply do not appear for warehouse-mode databases. REDO_GB_DAY and DB_SIZE_GB work normally, as does everything else. Closing the gap is tracked as a TODO on M11.1 in PLAN.md.

Opt-in

Scheduler jobs

A second standalone script, also outside install.sql. Both jobs it creates land DISABLED — nothing runs until you say so.

sqlplus · the schema that owns the suiteyou run
SQL> DEFINE report_dir = 'MY_DIR'   -- optional; default CAP_REPORTS
SQL> @install_jobs.sql

-- they arrive disabled; turn on whichever you want
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_ML_RETRAIN')
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_REPORT_SPOOL_JOB')

SQL> @uninstall_jobs.sql             -- drops both jobs + the procedure
What install_jobs.sql creates
ObjectScheduleDoes
CAP_ML_RETRAIN
job		 FREQ=WEEKLY, Sun 02:00 Calls cap_forecast_ml.train_all so the Tier 2 OML ESM models track the latest AWR days. Needs CREATE MINING MODEL.
cap_report_spool
procedure		 on demand Writes <dir>/cap_alerts.txt through UTL_FILE: a header (timestamp, database, CRIT/WARN/INFO counts) then one pipe-delimited line per CAPR_ALERTS row. Callable by hand: EXEC cap_report_spool('CAP_REPORTS').
CAP_REPORT_SPOOL_JOB
job		 FREQ=DAILY, 03:00 Calls that procedure with your report_dir. The _JOB suffix is not decoration: jobs and procedures share one schema namespace, so a job named CAP_REPORT_SPOOL beside the procedure fails with ORA-27477.
!

You must create the directory object yourself. That needs CREATE ANY DIRECTORY and a path decision only you can make, so the script refuses to guess: it checks ALL_DIRECTORIES and, if &report_dir (default CAP_REPORTS) is missing, prints the exact DDL to run — CREATE OR REPLACE DIRECTORY … AS '…' plus GRANT READ, WRITE ON DIRECTORY … TO <schema>. Without it CAP_REPORT_SPOOL fails with ORA-29280.

i

The spool job is not "the report". SQL*Plus spooling cannot happen inside a scheduler job — there is no SQL*Plus there — so what the job writes is a pollable alert snapshot, not the formatted capacity report. For the full report, keep driving report/report.sql from cron or your OS scheduler. Re-running install_jobs.sql is idempotent: it drops both jobs if present, then recreates them, again disabled.

Re-running it · upgrading

Idempotent, non-destructive re-install

Re-running the installer is safe: it rebuilds the views but never wipes what you've tuned, overridden or trained.

▸

Your knobs, overrides and models survive. Re-running @install.sql preserves all three persisted tables — the CAP_CONFIG knobs, your CAP_TBSPC_OVERRIDE rows and the CAP_ML_MODEL registry (with its OML models). The 00_drop step deliberately leaves those tables alone, and the config MERGE is INSERT-only — WHEN NOT MATCHED THEN INSERT, with no WHEN MATCHED branch — so it seeds keys that are missing and never overwrites a value you changed.

Upgrading is the same command. Pull the new revision and re-run @install.sql with the same seam_mode: every view is CREATE OR REPLACE, both tables are created only if absent, and any knob a new milestone added is MERGE-seeded with its shipped default while your existing values stay exactly as you set them. To reset one knob to its shipped default, DELETE that row and re-run ddl/05_config.sql (or just UPDATE it). Run @doctor.sql afterwards to confirm nothing came out INVALID. For a full teardown — views, types, package, OML models and all three tables — use @uninstall.sql.

The one caveat that bites

AWR retention bounds everything

Forecasts are only as long as the history behind them — and stock retention is short.

!

Default retention is only 8 days. That's far below the 90-day training window, so on a stock box local-mode forecasts degrade to INSUFFICIENT_HISTORY (TRAIN_N < min_train_days) and say so loudly. That is correct behaviour, not a bug — the report refuses to project a trend it can't yet see. doctor.sql checks 4 and 5 tell you this before you install.

To get real trends, raise AWR retention (here, to 90 days, expressed in minutes):

sqlplus · CDB$ROOTyou run
SQL> EXEC DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS(retention => 90*24*60);
i

This one is a real change to Oracle. Unlike everything else in this suite — which only ever SELECTs — MODIFY_SNAPSHOT_SETTINGS is a persistent AWR configuration change. It also only affects future snapshots: past history is not backfilled, so the training window fills in from the day you raise retention forward.

With that done, head to Usage to run the report and read its eight sections — or prove every part against known answers with the fixture self-check on Testing first.
