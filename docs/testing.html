Testing

Two ways to try it. Track A proves every part of the suite against known answers with deterministic fixtures; Track B runs the exact same code against real AWR.

Run Track A first — it installs synthetic data whose exact answers are worked out in advance and confirms the tool reproduces them, failing loudly if any number is off. Then Track B points the identical code at your live AWR to confirm it installs and reports end-to-end on a real 19c CDB. Both tracks run on your own 19c test box. A third, optional track — a real swingbench workload — is for when you want the toolkit to read genuine AWR history rather than fixtures.

Walkthrough · fixture data

What the fixture contains

Nothing in test/fixture_install.sql is random. Every series is a closed form, anchored to TRUNC(SYSDATE) so the training windows (which use SYSDATE) line up, and every expected answer is stored in CAP_FIXTURE_META so the self-check reads it rather than re-deriving it.

The snapshot spine

121 day indices i = 0..120, based at TRUNC(SYSDATE) − 120, with two snapshots a day under the fake dbid/con_dbid 42424242 (chosen so it can never collide with real AWR):

snap_idIntervalCarries
2000 + 2i18:00 (prev day) → 06:00 — the overnight intervalOSSTAT + time model + resource limits + redo size
2001 + 2i06:00 → 18:00 — the daytime / peak-window intervalthe same, plus every tablespace usage row (last-of-day)

Two holes are deliberate, and they fail in different ways:

  • The restart day (i = 60) has no 06:00 snapshot. Its single 18:00 snapshot carries a new startup_time and reset counters, so the one interval that day spans the restart and is thrown away by the startup-time guard — the whole day drops out of the CPU series (and out of REDO_GB_DAY).
  • The CPU gap day — the latest Sunday in i = 70..80 — keeps both of its snapshots but carries no OSSTAT / time-model rows at all. That is a pure AWR gap: the next 06:00 interval differences against 18:00 of the day before and spans 36 h. See the CPU section below.
i

Peak-window membership is by the interval's end hour, in (peak_hour_from, peak_hour_to] — the shipped (8, 18]. With this two-snapshot spine that means exactly the 18:00 snapshot is "peak" and the 06:00 one is not, which is what makes every busy_peak_pct / db_cpu_peak_pct expectation a closed form.

Tablespace series (ten of them)

All in the root container, 8 KiB blocks, one usage row per day off the 18:00 snapshot. Each one exists to pin down exactly one behaviour:

▸

Three CAP_TBSPC_OVERRIDE rows ship with the fixture. An exact-key row (2 GiB on FIX_OVERRIDE), a less specific (0,0) 1 GiB decoy for the same tablespace that must lose the specificity ranking, and a pure (0,0) wildcard exclusion for FIX_EXCLUDED. The fixture creates the table itself — a chicken-and-egg, since ddl/05_config.sql runs after the fixture install and ddl/00_drop.sql deliberately never drops it.

CPU — two containers

The CPU fixture has two containers, and the split is not cosmetic: host OSSTAT records under the CDB's con_dbid in real AWR, so giving a PDB its own OSSTAT rows would double host_busy_sec and break host_share_pct.

Containercon_dbidRowsShape
root — FIXCDB / CDB$ROOT 42424242 OSSTAT + time model (4 CPUs / 4 cores) weekday 20% night / 60% day (daily average 40%), weekend 10% / 30% (avg 20%), one injected Tuesday at 70% / 70%, the restart at day 60 and the Sunday AWR gap
PDB — FIXCDB / FIXPDB1 42424243 time model only — no OSSTAT a 7-day DB_CPU_PCT sawtooth 34,36,…,46 that steps +18 points for the last 7 days

Closed forms on a plain probe weekday in the root container: busy_pct = 40, busy_p95 = 58 (PERCENTILE_CONT(0.95) of {20, 60}), busy_max = 60, busy_peak_pct = 60 (the daytime interval alone), host_busy_sec = 138240, db_cpu_sec = 400 and db_cpu_pct = 0.1157.

▸

The gap day is a guard test, not a detection test. The day after the Sunday gap carries one 36 h interval plus the normal 12 h daytime one, so it reads 30% busy against a 40% Monday baseline — 10 points off, past the 9-point threshold. It would flag. It must not, purely because gap_flag = 'Y' suppresses scoring. Meanwhile busy_p95 still reads 60, from the 12 h interval alone: the 36 h interval averages 20% and is excluded from p95/max as too long to be a "peak hour". (An unfiltered p95 of {20, 60} would be 58 — that difference is the assertion.)

▸

Why the level shift rides on DB_CPU_PCT. The sawtooth means any 7 consecutive days contain each offset exactly once, so both medians are exact: base_med = 40 over the 28-day baseline, recent_med = 58 over the shifted last 7 — shift_pct = 18, with a real base_mad_sigma = 4 × 1.4826 = 5.93 for the N-of-M confirmation to clear. And the shift is invisible to every other layer: the PDB has no OSSTAT, the daily CAPA_CPU_ANOM does not cover that metric, and the trend fit reads the step as noise. CAPA_CPU_SHIFT is the only thing that can say the container now runs 18 points hotter than it did a month ago.

The t ≈ 1.96 + 2.4/df approximation is part of the contract. There is no t-distribution in SQL, so ddl/30_forecast_views.sql approximates the 95% multiplier that way (good to ~1% for df ≥ 10, and min_train_days guarantees df ≥ 12). The fixture installer computes its expected bands with the same formula — that is deliberate, and it means the two are a matched pair: change the view's multiplier without changing the installer's and the FIX_ZIGZAG interval assertions break. Change both together, on purpose.

Run the preflight

doctor.sql is a read-only PASS/WARN/FAIL checklist and the fastest way to find out whether local mode can work here — before you install anything. It checks Diagnostics Pack access, direct SELECT on each DBA_HIST_* view the local seam needs, the CREATE TABLE/VIEW/PROCEDURE/TYPE/MINING MODEL/JOB privileges, AWR retention and snapshot interval per dbid, how many distinct days each source actually holds versus min_train_days, and — if the suite is already installed — invalid CAP* objects plus the seam mode in use. It closes with a plain-English reason why forecasts would come back INSUFFICIENT_HISTORY. Every probe is exception-wrapped, so a missing privilege prints one WARN line instead of aborting.

Walkthrough · optional

Track C — a real workload (bench/)

The fixtures prove the arithmetic. They cannot prove the toolkit reads a live database sensibly — an idle test instance produces INSUFFICIENT_HISTORY everywhere and nothing to detect. bench/ is a swingbench harness that generates shaped daily load so the forecast and anomaly views have genuine AWR history to work on.

Everything in bench/ is optional: the suite never depends on it, and install.sql installs nothing from it into the database.

What it drivesWhy the forecaster needs it
SOE (Order Entry) OLTP insertsgrow SOETBS monotonically — the input CAPF_TBSPC_FORECAST / days-to-full actually needs
SH (Sales History) rollups and cubesburn CPU with essentially no growth, so the CPU and tablespace series move independently
Weekday / weekend contrastgives dow_weeks (the same-weekday CPU baseline) a real seasonal signal
anomaly_load.sql + a 24-user bursta genuine outlier for CAPA_TBSPC_ANOM / CAPA_CPU_ANOM to find

The daily shape runs as six phases — ramp (4 SOE users, 45 min), peak (16 users, 60 min, CPU near cpu_sat_pct), dss (3 SH users, 30 min), mixed (8 SOE + 2 SH, 45 min), batch (6 users, 20 min, redo/undo heavy) and anomaly (24 users, 30 min). run_phase.sh forces an AWR snapshot either side of each phase, so phase boundaries line up with snapshot boundaries; weekday-only phases self-skip at weekends and the ones that do run halve their user count.

workstation · bashyou run
cp bench/env.sh.example bench/env.sh && $EDITOR bench/env.sh   # once — the only place credentials live

./bench/setup/setup.sh                # AWR settings + tablespaces + both schemas
./bench/run_day.sh --short            # ~50 min smoke run
./bench/run_phase.sh peak             # a single phase
crontab bench/cron/bench.crontab      # daily shape from here on

./bench/teardown.sh                   # drop it all, restore the AWR settings
!

It changes AWR settings and creates schemas. bench/setup/01_awr_settings.sql switches the CDB to 15-minute snapshots with 35-day retention, and 02_bench_objects.sql creates SOETBS / SHTBS (capped autoextend) plus a PDB-local wizard DBA. That is not read-only — test boxes only. teardown.sh reverses all of it.

▸

Watching the machinery before 14 days have passed. Forecasts stay INSUFFICIENT_HISTORY until min_train_days daily points exist. On a test database only, lower the gate temporarily — UPDATE cap_config SET cfg_value = 3 WHERE cfg_name = 'min_train_days'; — and put it back to 14 afterwards. And if SOETBS grows too slowly to give a useful forecast, lower TBS_MAXSIZE rather than pushing more concurrency at the VM: days_to_full is only meaningful against a bounded tablespace.

Full detail — layout, the per-phase table, sizing notes for a small VM, and the queries that tell you the load reached the seam — is in bench/README.md.
