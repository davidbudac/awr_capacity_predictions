Guide

Usage

Generate the read-only report, read it, drill into anything that looks wrong, poll the alert view from your monitoring stack, and tune everything through config rather than SQL.

The report has eight sections. Read them top to bottom, drill into any row you don't believe, and wire CAPR_ALERTS into whatever already pages you. Nothing here writes to your AWR data.

Generate

Run the report

One script, run from the repo root. A bare run never prompts and spools a plain-text file.

SQL*Plusyou run
sqlplus / as sysdba              -- or any monitoring schema
SQL> @report/report.sql               -- everything from report/defaults.sql
SQL> @report/report.sql 5             -- top_n=5, the rest defaulted
SQL> @report/report.sql 5 7 N         -- top_n / anomaly_days / show_esm
SQL> @report/report.sql 10 30 AUTO 42424242 42424243   -- one container only
SQL> @report/report.sql - - - - - SNAPSHOT             -- from the last refresh run

Launch it from the repo root: SQL*Plus resolves @@ includes relative to the outermost caller on 19c, so report/report.sql must be started from the repository directory. It auto-loads report/defaults.sql, so a bare run never prompts, and it spools to reports/cap_report_<db>_<ts>.txt. The report is read-only — it only SELECTs, and creates or modifies no database object. Identity comes from SYS_CONTEXT, so no V$ or catalog privileges are needed.

The positional arguments — [top_n] [anomaly_days] [show_esm] [dbid] [con_dbid] [source]; - skips one
PositionNameDefaultDoes
1top_n10Rows in the days-to-full, near-full, forecast and ESM-compare rankings.
2anomaly_days30Trailing days of anomalies printed in sections 3 and 5. Presentation only — CAPR_ALERTS has its own window, the anomaly_report_days knob (14).
3show_esmAUTOAUTO = show section 6 only if OK models exist, else print a one-line hint; Y = always show it; N = skip it. Case-insensitive.
4dbideveryShow only this database in every section; top_n then ranks inside it.
5con_dbideveryShow only this container (pass - for the dbid to scope on the container alone).
6sourceLIVELIVE evaluates the views now. SNAPSHOT reads the alert list (CAPR_ALERTS_LATEST) and the section 1 and 7 fits (CAPR_FIT_HISTORY) of the newest OK refresh run of the results layer, which is fast; the header says which run. The other sections stay live.
▸

Presentation lives in one file — or on the command line. To change these three for every run, edit report/defaults.sql, the single source of truth both drivers load. To change one run, pass them positionally; an omitted argument falls back to that file, and neither form ever prompts. Both scripts UNDEFINE the arguments at the end, so a later argument-less call in the same session can't silently inherit them. Everything else is analytics config — see Configuration below.

CSV and cron

@report/report_csv.sql [dbid] [con_dbid] writes one CSV per CAPR section view (alerts, days to full, forecast, anomalies, CPU trend and shifts, series, fit) into reports/cap_csv_<db>_<ts>/: every column, every row in the scope, a header line, every value quoted. For a scheduled run, report/run_report.sh [connect] [--html] [--csv] [--scope D[:C]] [--snapshot] [--keep N] [--container PDB] [--schema OWNER] runs the drivers from the repo root, prints each file it wrote, and exits non-zero when a spool is missing or contains an ORA- or SP2- line, so cron can alert on it.

crontabdaily 06:30
30 6 * * * . ~/.bash_profile; /opt/awrcap/report/run_report.sh "/ as sysdba" --html --keep 14 >> /var/log/awrcap_report.log 2>&1
Generate · alternative

HTML report

A sibling driver renders the same sections as one self-contained HTML dashboard instead of plain text — open the spooled file directly in a browser.

SQL*Plusyou run
sqlplus / as sysdba              -- run from the repo root
SQL> @report/report_html.sql        -- spools reports/cap_report_<db>_<ts>.html
SQL> @report/report_html.sql 25 60 Y  -- same three positional arguments

report/report_html.sql shares the same defaults file, the same knobs, and the same read-only guarantee as the text report — the HTML is assembled in one PL/SQL block via DBMS_OUTPUT and captured by SPOOL. It opens with a verdict strip (critical, warnings, forecast quality, host CPU p95, Tier 2 models, the last refresh run and data coverage) and a ranked attention list built from CAPR_ALERTS: one row per issue with the number that matters at the right, and one line naming everything that is healthy. Then come the charts, all drawn with one grammar: area under history, the 95% prediction band as a shaded wedge, a labelled ceiling or saturation line, a “today” divider, hollow rings on unusual days, the ESM point with its interval (at the model's furthest step, labelled "ESM +N days"), and the date printed where the projection crosses the ceiling. The whole-database hero reads the suite's own DB_SIZE_GB fit, so it prints the same days figure as section 7. Tablespaces that need a look get a card with days-to-full as the big figure; flat or far-from-full ones collapse into a one-row sparkline strip. CPU shows the busy-hour p95 (what saturates) and each container’s DB CPU as a share of the host’s logical CPUs, with any sustained level shift shaded. Unusual days are dot strips per series with the numbers folded underneath, and Tier 2 vs Tier 1 is one row per series with the backtest verdict. Each section renders inside its own exception block: a broken view prints a red block for that section, the footer counts it, and the rest of the page survives. Every column header carries a plain-English tooltip, the glossary sits in one “How to read this report” fold, and it all renders as plain <svg> with no chart library and no external assets, plus a sticky section nav and a light/dark toggle. See the sample report.

i

The two drivers read the same rows. Both consume the CAPR_ per-section views, where every derived number, label, severity marker and unit conversion is computed once; only chart geometry is calculated in the HTML driver. The text and HTML reports therefore cannot show different numbers.

Interpret

Reading the report

Eight sections, top to bottom, each backed by one CAPR_ view.

Sections 0–7 and the views behind each
#SectionWhat to read
0At a glance
CAPR_ALERTS		 CRIT / WARN / INFO counts, then one line per current issue: severity, kind, DB/PDB and a ready-to-page message. The same view the HTML banner and any external poller read, so they can never disagree. Its anomaly kinds use the anomaly_report_days knob, not this report's anomaly_days. The header above it prints the data-through date, the last refresh run and the coverage line (CAPR_COVERAGE); a DATA_STALE row comes first. With SNAPSHOT the list is the open, not acked states of the last refresh run.
1Days-to-full & near-full
CAPR_TBSPC_DAYS_TO_FULL		 1a ranks tablespaces by days_to_full at any fit quality — a LOW_CONFIDENCE estimate is still a signal, and the QUALITY column says how far to trust it. CRIT at/below dtf_crit days, WARN at/below dtf_warn; ACCEL > 1.5 means growth is accelerating. WORST/BEST bound the estimate with the 95% CI on the slope (empty BEST = might never fill). 1b re-ranks by PCT_USED alone, independent of fit quality, so a 97%-full tablespace whose fit is unusable can never vanish from the report. GATE says why a row inside the warning window does not page (low-q, cyclic, stale), so the SEV column matches what CAPR_ALERTS raises. NEED_90_GIB is the sizing ask: space to add so the upper 95% band stays under the ceiling for 90 days; ADD_BY is the worst-case fill date. A CYCLIC tablespace is ranked on its peak line.
2Tablespace forecast
CAPR_TBSPC_FORECAST		 Current / +30 / +90 / +180 GiB with TRAIN_N, R², quality, and the ESM column when Tier 2 models exist: ESM_GIB sits ESM_H days after the last day, the model's furthest step (at most 30) minus its age. 180_LO/180_HI are the 95% prediction band on the widest printed horizon. Bounded: a tablespace prints only if it is growing, near-full, or at least report_min_gb GiB used, then capped at top_n — the header states how many of the total it is showing.
3Tablespace anomalies
CAPR_TBSPC_ANOMALIES		 Flagged days inside anomaly_days, one line per (day, baseline mode), each fully justified: the day's growth rate (delta ÷ gap), the baseline median rate, the threshold max(k·MAD, 100 MiB/day floor), the robust z and N_HIST, the number of baseline days. MODE says which baseline flagged it: TRL (the last mad_window_days) or DOW (the same weekday over dow_weeks). A day can flag under one mode and not the other. GAP is days since the previous sample, greater than 1 across an AWR gap, which is why the rate and not the raw delta is scored.
4CPU trend
CAPR_CPU_TREND		 Six metrics per container: BUSY_PCT (daily average), BUSY_P95 and BUSY_PEAK (the busy hour — p95 of the day's intervals, and the peak_hour_from/peak_hour_to window), plus DB_CPU_SEC, DB_CPU_PCT and DB_CPU_P95 for this container's DB CPU as a share of the host's logical CPUs (NUM_CPUS, capped by cpu_count). DAYS_SAT projects when the metric reaches cpu_sat_pct (every metric except DB_CPU_SEC, which has no percentage ceiling), with the same WORST/BEST slope-CI range, starting from the smoothed anchor (the median of the last shift_days complete days). SIG = Y when the slope is outside its own 95% CI (the default quality gate), HOT = Y when the recent p95 median is already at or above cpu_sat_pct (a CPU_HOT / DBCPU_HOT alert), and GATE says why a row does not page.
5CPU anomalies & level shifts
CAPR_CPU_ANOMALIES · CAPR_CPU_SHIFTS		 5a lists flagged CPU points: host BUSY_PCT and each container's DB_CPU_PCT (METRIC), scored against three baselines (MODE): TRL (the last 28 days), DOW (the same weekday) and HOW (the same weekday and hour, so a day with a normal average but an inverted profile still shows). WHEN is the day, or the day, weekday and hour for an HOW row. Weekly seasonality is handled deterministically rather than modelled. 5b catches the other failure mode: a sustained step rather than a one-day outlier. The recent window's median is compared with the baseline median before it, and flags only when the gap exceeds shift_min_pct points and every day of the recent window sits above (UP) or below (DOWN) the baseline median ± its MAD-sigma — the N-of-M column shows that count.
6ESM compare & backtest
CAPR_ESM_COMPARE · CAPR_BACKTEST		 6a tablespaces and 6b CPU, Tier 2 beside Tier 1 at each horizon with the ESM CI; ESM_MODEL names the variant (HOLT or ADDW, i.e. EXSM_ADDWINTERS with a 7-day season). 6c is the holdout scorecard — see Backtest below. 6a shows exactly the same tablespaces as section 2 (four horizons each). With show_esm=AUTO and no models, the whole section collapses to a one-line hint.
7Fixed-ceiling series
CAPR_SERIES · CAPR_SERIES_ANOMALIES		 Four series that share one property — each has, or conspicuously lacks, a single hard ceiling. PROCESSES and SESSIONS are peak concurrency (the AWR high-water mark since instance startup, summed across RAC instances) against the matching init parameter. REDO_GB_DAY is redo written per day; it has no ceiling and is a trend for FRA / archive-destination sizing. DB_SIZE_GB is total permanent-tablespace bytes used against the summed tablespace ceilings. ASM_DG:+<group> is a diskgroup's GiB used against its total, and TEMP_PEAK:<ts> / UNDO_PEAK:<ts> the day's highest sampled TEMP / UNDO usage against its maxsize. FRA_DAYS on the REDO_GB_DAY row is db_recovery_file_dest_size over the current redo rate. DAYS_LIM projects when the series reaches series_sat_pct% of its limit — 90% by default, because hitting processes exactly is an outage, not a warning. 7b lists the flagged anomalies of these series (CAPR_SERIES_ANOMALIES), one line per (day, mode): PROCESSES, SESSIONS and REDO_GB_DAY on their level, DB_SIZE_GB on its daily growth in GiB.
!

Read QUALITY before you read the number. Only OK is a trustworthy fit. LOW_CONFIDENCE means R² fell below r2_gate, FLAT means the slope is exactly zero, and INSUFFICIENT_HISTORY means fewer than min_train_days daily points — raise AWR retention, then wait. The report prints these loudly rather than quietly projecting a line it can't support.

Verify

Drill into one series

When a report row looks wrong, re-derive it with a pocket calculator.

SQL*Plus · repo rootyou run
SQL> @report/drill_tbspc.sql SYSAUX            -- name REQUIRED
SQL> @report/drill_tbspc.sql SYSAUX 2482321331 -- ... in one container only

SQL> @report/drill_cpu.sql                     -- BUSY_PCT, all containers
SQL> @report/drill_cpu.sql BUSY_P95
SQL> @report/drill_cpu.sql DB_CPU_PCT 2482321331

Each prints to screen and spools reports/cap_drill_<name>_<ts>.txt containing four blocks: the fit header (slope, intercept, R², the 95% slope CI, days-to-full or days-to-saturation with its WORST/BEST range); the daily series over the train_days window — actual, fitted icept + slope · day_n, residual, day-over-day delta, AWR gap and that day's median / MAD-sigma / threshold / robust-z; a residual footer showing SUM(residual) (zero by construction) and re-deriving resid_se = sqrt(SSE/(n−2)) and the slope CI from scratch next to the values the view publishes; and anomaly arithmetic, one spelled-out line per flagged (day, mode) with the CAP_CONFIG knob values shown. The daily series shows the TRAILING and the SAME_DOW baseline side by side, and the window starts at train_start, so the footer reconciles with the view after a reset. drill_tbspc.sql ends with who is filling it: the top 10 segments by space allocated over the last seg_window_days (28), with each one's share of the tablespace's growth, from CAPR_SEGMENT_GROWTH over DBA_HIST_SEG_STAT. AWR keeps only the top segments of each snapshot, so a small grower can be missing.

drill_cpu.sql's metric argument is optional and defaults to BUSY_PCT; the valid values are the six in section 4. Anomalies are scored for BUSY_PCT and DB_CPU_PCT only, so the anomaly columns read n/a for the other four. For those two metrics the script adds a block of flagged HOUR_OF_WEEK hours: weekday and hour, baseline size, expected value, sigma and threshold. drill_tbspc.sql requires a tablespace name — without one it prints usage and stops. Both are read-only, never prompt, and UNDEFINE their arguments at the end.

Integrate

Polling CAPR_ALERTS

One row per current issue, shaped for an OEM metric extension, Zabbix, Nagios, or a scheduler job.

SQL*Plusexample
SQL> SELECT severity, kind, db_pdb, message
  2    FROM capr_alerts ORDER BY sev_rank;

-- alarm on the numbers, without parsing the message text
SQL> SELECT kind, db_pdb, series_key, value, threshold, unit
  2    FROM capr_alerts WHERE severity = 'CRIT';

Every row carries severity (CRIT/WARN/INFO) with a numeric sev_rank (1/2/3) to sort by, the kind, the (dbid, con_dbid) keys plus a resolved db_pdb label, the series_key (tablespace name, CPU metric or series name), the observation day_dt, the value that crossed its threshold with a unit, a ready-to-page message, the baseline_mode that raised an anomaly kind (NULL for every other kind) and an alert_key (dbid|con_dbid|kind|series_key|YYYY-MM-DD|mode) that is unique, so a poller can de-duplicate on it. Since M19 each row also carries a state_key (kind|dbid|con_dbid|series_key|mode, the same from one day to the next, which the results layer tracks), direction (LE for days-to-limit kinds, GE for percent and age kinds, ABS for anomalies and shifts), alarm_threshold (the WARN line, whatever the severity) and is_current; an anomaly episode adds first_day, n_days and max_z. Alarm on value vs threshold; the message is for the human who gets paged. Forecast kinds fire only for a current series (is_current = 'Y'), and their severity comes from CAPR_SEVERITY, which honours a tablespace's own thresholds in CAP_TBSPC_OVERRIDE.

i

The alert window is not the report window. The anomaly kinds use anomaly_report_days (14) from CAP_CONFIG; sections 3 and 5 of the report use the anomaly_days presentation knob (30). They are deliberately different: one bounds what pages you, the other bounds what you read.

▸

Every mode is scored; the bitmask decides what pages. CAPR_ANOMALIES lists every flagged (point, mode) with alerting = Y or N, and the anomaly rows of CAPR_ALERTS are its alerting = 'Y' rows. To page on the hour-of-week baseline as well as the same-weekday one, add the bits: UPDATE cap_config SET cfg_value = 6 WHERE cfg_name = 'alert_modes_cpu'; (2 = SAME_DOW + 4 = HOUR_OF_WEEK). 0 turns a family's anomaly alerts off without hiding the anomalies.

i

One row per episode, quieter during a shift. Consecutive flagged days of one series and mode arrive as one row: its message starts "N consecutive days, latest …, peak robust z …" and first_day / n_days / max_z carry the numbers. A per-day CPU anomaly inside an active CPU_SHIFT window drops to INFO "(level shift active)": the shift row already says it.

Integrate

Alert state, acknowledgement and the weekly digest

CAPR_ALERTS is evaluated live and remembers nothing. The results layer adds the memory: run history, one state per alert, an ack, and the change feed.

SQL*Plusyou run
SQL> EXEC cap_results.refresh                     -- or enable CAP_REFRESH_JOB (daily 01:30)
SQL> SELECT severity, kind, db_pdb, message, age_days, events_since
  2    FROM capr_alerts_latest ORDER BY sev_rank;   -- open, not acked, as of the last run

-- acknowledge: hidden until the date (NULL = until it resolves)
SQL> EXEC cap_results.ack('TBSPC_FULL|3141592653|3141592654|AUDIT_TRAIL|-', SYSDATE + 7, 'disk ordered, CHG0042')
SQL> EXEC cap_results.unack('TBSPC_FULL|3141592653|3141592654|AUDIT_TRAIL|-')

SQL> SELECT * FROM capr_alert_events WHERE run_id > :last_run_id;   -- poll the changes
SQL> SELECT * FROM capr_weekly_digest;                             -- this week vs last

cap_results.refresh records a run in CAP_RUN (RUNNING, then OK, or FAILED with the error stack and re-raised so a scheduler run fails too), copies CAPR_FIT into CAP_FIT_HIST, and merges CAPR_ALERTS by state_key into CAP_ALERT_STATE. Each change writes a CAP_ALERT_EVENT: NEW, ESCALATED, DEESCALATED, RESOLVED (after resolve_grace_runs, 2, runs without it) and REOPENED. It commits; call it with no pending work of your own. ack takes a state_key or the last alert_key the state carried; an escalation or a reopen clears the ack. cap_results.purge(p_keep_days) (default 400) trims old runs, and cap_results.reset forgets everything, acks included.

Views over the results tables (all of them work on empty tables)
ViewAnswers
CAPR_ALERTS_LATESTWhat is open and not acked right now, how old it is and how many events it had since it opened. A table read, so it is fast; the SNAPSHOT report reads it.
CAPR_ALERT_EVENTSEvery state change, newest first, with the run's as_of_day and the previous severity. Poll it with run_id > :last.
CAPR_RUNSEvery refresh run, its duration and one-line summary; stale_run = 'Y' when the last OK run is older than refresh_stale_hours (36).
CAPR_WEEKLY_DIGESTThe latest run against the latest one at least digest_days (7) older, per series: days to full then and now, percent used, quality and severity then and now, a change verdict, and the alerts that opened, resolved or reopened in between.
CAPR_FORECAST_ACCURACYWhat each stored fit projected (value_then + slope_then × elapsed_days) against what the series reads now. Filter on elapsed_days for a horizon.
CAPR_FIT_HISTORYThe stored fits of the OK runs, for trend-of-the-forecast questions ("how has days to full moved this month?").
CAPR_COVERAGELive, per dbid: newest snapshot and its age, days of history, retired flag, and series by quality. Both reports print its one-line summary.
Integrate · optional

Kibana dashboards (ELK)

If you already run an Elastic stack, elk/ ships the same analytics the reports print into one index and installs three Lens dashboards. It is entirely optional and lives outside install.sql.

The path is the one the rest of your Oracle telemetry already takes: a script on the database host writes NDJSON, Filebeat tails it, Logstash indexes it. Nothing on the database host talks to Elasticsearch, and nothing writes to Oracle.

What ships, one record type per row
RecordOne perDrawn as
observationcontainer × series × day, with cap.anomaly = true on days the CAPA_ layer flaggedthe observed line; flagged days as a red bar under it
forecastcontainer × series × method × horizon (REGR anchors, the ESM point at the model's furthest step) with its bandthe line to the right of today, plus low/high
fitcontainer × series × export day: slope, R², quality, days to full/limit/saturation, severitythe days-to-full and trend tables, colour-coded
anomalyflagged event: growth outlier, CPU or DB CPU outlier, series outlier (one per baseline mode), or a CPU level shift, with a one-line explanationthe fleet anomaly board and per-board anomaly tables
alertCAPR_ALERTS row × export daya compact alerts table on every board

Three dashboards: Tablespaces (days to full, observed + forecast + band, daily growth, growth anomalies), CPU and workload series (host CPU against the saturation line, DB CPU level shifts, sessions / processes / DB size / redo against their limits) and Fleet anomalies, which shows only anomalies across every database, newest first, and drills into the other two.

shellinstall
# stack side, once (index template, data view, dashboards)
$ elk/setup.sh
$ cp elk/logstash/oracle_capacity.conf <logstash pipeline dir>/   # beside the Oracle pipeline

# database host, as the Oracle owner, with Filebeat deployed
$ cp elk/filebeat/awrcap.yml /u01/app/oracle/filebeat/inputs.d/
$ elk/export.sh --sid cdb1          # daily; validates against the mapping, appends NDJSON

Documents carry deterministic ids, so a re-export overwrites rather than duplicates. The index mapping is strict and the exporter checks every document against it before Filebeat sees it. Everything else, including how to add a field or regenerate a dashboard, is in elk/README.md.

Integrate · optional

Grafana dashboards (ORDS, no Elastic)

The second visual path keeps the data in Oracle. ORDS (Oracle REST Data Services) publishes seven read-only views as JSON and Grafana's Infinity data source reads them live, so every refresh is a query against the suite's own views and nothing is copied anywhere.

shellinstall
# 1. ORDS against the database (lab recipe: grafana/ords/README.md)
# 2. publish the module, as the schema owner (or a DBA with ORDS_ADMIN)

# 3. Grafana with the Infinity plugin, data source and dashboards provisioned

i

Live has a cost. Every refresh runs the forecast and anomaly views, which take seconds at fixture size, and a module serves one schema. Pick this path when you have Grafana and no Elastic; pick the ELK path when the fleet already lives there or you want a daily history of the fits. Contract, limits and security notes are in grafana/README.md.

Integrate · optional

Oracle APEX application (nothing outside the database)

The third visual path needs no Elastic stack, no Grafana and no REST module. An APEX application imported into a workspace on the suite's schema reads the same CAPR_ views with APEX's own Oracle JET charts and Interactive Reports. Every view is loaded once per session into an APEX collection, so the pages stay fast while the data stays live; a Refresh data button reloads it and a freshness badge shows the latest observed day per database.

Trust the ceiling

Reading limit_source, and overriding the limit

A days-to-full is only as honest as the limit it counts down to.

CAPF_TBSPC_FORECAST (and CAPR_TBSPC_FORECAST above it) publishes limit_source, which says where that ceiling came from:

limit_source — three possible answers
ValueMeans
OVERRIDEA CAP_TBSPC_OVERRIDE row set the ceiling by hand. This one you can trust, because you wrote it.
AUTOEXTENDThe summed datafile maxsize recorded in AWR. Trustworthy only if the storage underneath can actually deliver it.
ALLOCATEDNo autoextend — the currently allocated size is the ceiling.
!

AUTOEXTEND is a promise the storage may not keep. A 32 GiB datafile maxsize on a 10 GiB filesystem or ASM diskgroup is not 32 GiB of headroom, and a days-to-full computed against it is a comfortable lie. When you know the real ceiling, state it.

Tune · per tablespace

CAP_TBSPC_OVERRIDE

Set the real ceiling, or silence the staging tablespace that is supposed to fill up. MERGE so the statement is re-runnable.

SQL*Plusexample
-- the real ceiling is the 200 GiB diskgroup, not the 2 TB datafile maxsize
MERGE INTO cap_tbspc_override t
USING (SELECT 1234567890 AS dbid,
              2345678901 AS con_dbid,
              'APPDATA'  AS tablespace_name,
              200 * 1024 * 1024 * 1024 AS limit_bytes,
              'N'        AS exclude_flag,
              'DG +DATA is 200G; maxsize is fiction' AS note
       FROM   dual) s
ON     (t.dbid = s.dbid AND t.con_dbid = s.con_dbid
        AND t.tablespace_name = s.tablespace_name)
WHEN MATCHED THEN UPDATE
     SET t.limit_bytes  = s.limit_bytes,
         t.exclude_flag = s.exclude_flag,
         t.note         = s.note
WHEN NOT MATCHED THEN
     INSERT (dbid, con_dbid, tablespace_name, limit_bytes, exclude_flag, note)
     VALUES (s.dbid, s.con_dbid, s.tablespace_name,
             s.limit_bytes, s.exclude_flag, s.note);

-- stop forecasting the nightly-truncated staging tablespace, in EVERY database
MERGE INTO cap_tbspc_override t
USING (SELECT 0 AS dbid, 0 AS con_dbid, 'STAGING' AS tablespace_name,
              CAST(NULL AS NUMBER) AS limit_bytes, 'Y' AS exclude_flag,
              'reloaded nightly -- growth is meaningless' AS note
       FROM   dual) s
ON     (t.dbid = s.dbid AND t.con_dbid = s.con_dbid
        AND t.tablespace_name = s.tablespace_name)
WHEN MATCHED THEN UPDATE
     SET t.limit_bytes  = s.limit_bytes,
         t.exclude_flag = s.exclude_flag,
         t.note         = s.note
WHEN NOT MATCHED THEN
     INSERT (dbid, con_dbid, tablespace_name, limit_bytes, exclude_flag, note)
     VALUES (s.dbid, s.con_dbid, s.tablespace_name,
             s.limit_bytes, s.exclude_flag, s.note);

COMMIT;
How a row is matched
ColumnRule
tablespace_nameMatched exactly. No patterns, no wildcards.
dbid · con_dbid0 is a wildcard meaning "any". So (0, 0, 'STAGING') is a fleet-wide rule, (dbid, 0, 'STAGING') is per-database, and naming both is per-container.
most specific winsWhen several rows match one tablespace, a real dbid beats the 0 wildcard first, then a real con_dbid does.
limit_bytesThe real ceiling in bytes. NULL keeps the computed limit — useful on a row that exists only to set exclude_flag.
exclude_flag'Y' drops the tablespace from CAPD_TBSPC_DAILY and therefore from forecasts, anomalies, alerts and both reports. Defaults to 'N'.
dtf_warn · dtf_critThis tablespace's own days-to-full thresholds. NULL = the knob. Every alert and both reports read the effective value (eff_dtf_warn / eff_dtf_crit in CAPR_TBSPC_DAYS_TO_FULL), and CAPR_SEVERITY reports thr_source = 'OVERRIDE'.
nearfull_warn_pct · nearfull_crit_pctThis tablespace's own near-full thresholds, same rule. A row may carry only thresholds, with limit_bytes NULL and exclude_flag 'N'.
noteFree text, for whoever reads the table in six months.

The override is applied once, in CAPD_TBSPC_DAILY, so every layer above it honours it automatically — no re-install, no view change. Your rows survive @install.sql and are removed only by @uninstall.sql.

Optional · Tier 2

Tier 2 (OML ESM)

Train one Oracle Machine Learning model per series for a seasonality-aware second opinion, then re-run the report to populate section 6.

SQL*Plusyou run
SQL> EXEC cap_forecast_ml.train_all(20);       -- top-20 tablespaces + CPU series + their backtest twins
SQL> EXEC cap_forecast_ml.train_tablespace('ORDERS_DATA');   -- retrain one series
SQL> @report/report.sql                        -- section 6 now shows ESM vs REGR

SQL> EXEC cap_forecast_ml.drop_all;            -- remove the models again

Training needs the CREATE MINING MODEL privilege (free in all editions since Dec 2019). With esm_tbspc_model at its default of AUTO, train_all trains both EXSM_HOLT and EXSM_ADDWINTERS(7) as holdout twins per tablespace and keeps whichever scored the lower backtest MAPE — set esm_select_by_backtest to 0 to skip those two extra trainings and let AUTO fall back to Holt, or pin the type outright with 0 or 1. train_all also refreshes the backtest twins of the series it trains (p_backtest => FALSE skips them). Each build runs under a temporary name and replaces the old model only when it succeeded; a failure keeps the previous model, records FAILED with last_error in CAP_ML_MODEL, and the procedure raises ORA-20060 after the batch. CAPF_ESM_HEALTH lists every model, the report headers print "N ok, F failed, S stale", and MODEL_HEALTH alerts on it. To automate the refresh daily, see Scheduler jobs below.

!

Tier 2 never reaches past +30 days. Oracle 19c hard-caps EXSM_PREDICTION_STEP at 30 at any series length, and the package also caps it at a quarter of the series length (90 days of history give a 22-step model). CAPF_COMPARE shows the model's furthest step in the +30 row while the model is at most esm_max_age_days (7) older than its series' last day; section 6 prints the step when it is not +30, and the model age. The +90 / +180 / +365 columns are always REGR-only.

Interpret · section 6c

Reading the backtest

Which engine was actually right, over a window where you already know the answer.

Section 6c replays the recent past: each engine forecasts the last backtest_holdout_days (28) from data before the cutoff, and is scored against what really happened. MAPE% is the mean absolute percentage error — lower is better. BIAS% is signed: positive means the engine over-forecast. BETTER names the engine with the lower MAPE, and is empty when one of the two has no score to compare. CUTOFF is the day the holdout starts.

ESM_PICK explains the AUTO decision in one column: either ADDW H=2.90 W=1.20 — the chosen type followed by the Holt and AddWinters MAPEs that decided it — or HOLT (config) when the type was pinned by esm_tbspc_model instead of measured.

i

REGR is scored with or without models; ESM needs the twins. The REGR_MAPE / REGR_BIAS columns work on a fresh install — CAPF_BACKTEST is queryable any time. The ESM columns fill only after cap_forecast_ml.train_backtest. Expect ESM to cover fewer days than REGR: the backtest twins inherit both the 19c 30-step cap and the package's FLOOR(rows/4) floor, and n_days reports the coverage each engine actually achieved.

Tune · the estimator

Switching to Theil–Sen or DRIFT

One knob swaps the slope estimator for every CAPF_ fit.

SQL*Plusexample
SQL> UPDATE cap_config SET cfg_value = 1 WHERE cfg_name = 'slope_method';
SQL> COMMIT;   -- 0 = OLS (default), 1 = Theil-Sen, 2 = DRIFT

-- ts_slope_bpd is computed only under 1; drift_slope_bpd always
SQL> SELECT tablespace_name, slope_method, ols_slope_bpd, ts_slope_bpd
  2    FROM capf_tbspc_forecast ORDER BY tablespace_name;

CAP_CONFIG is numeric, so the encoding is 0 = OLS (REGR_SLOPE, the default) and 1 = THEILSEN, the median of the pairwise slopes. Theil–Sen is worth reaching for when a series carries a one-off step — a bulk load, a migration — that drags a least-squares line off the underlying trend. The chosen estimator drives the slope, intercept, projections, days-to-full, days-to-saturation, accel_ratio and the FLAT test; the slope_method column on each row says which one that row used, and both slopes stay visible as ols_slope_bpd and ts_slope_bpd so you can see what changed.

i

R² and the prediction bands stay OLS. There is no closed-form Theil–Sen interval in SQL, so r2, resid_se, the projection bands and the slope CI remain OLS residual quantities — drawn around whichever line you chose. That is a deliberate v1 trade-off, not an oversight.

▸

A related knob for the other kind of step. Where Theil–Sen tolerates a step, reset_on_shrink (on by default) removes one: after the most recent large shrink in a tablespace, the training window restarts at that day — its used_bytes is already post-purge — so the fit describes the series as it is now rather than averaging across the cliff. shrink_mad_k (6) sets how big a drop has to be to count; it is deliberately higher than mad_k because it restarts a fit.

Scheduler jobs

Optional, and installed separately — see Advanced install for the setup and the directory-object requirement.

SQL*Plusyou run
-- every job arrives DISABLED; enable whichever you want
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_REFRESH_JOB')      -- daily 01:30, results layer
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_ML_RETRAIN')       -- daily 02:00
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_REPORT_SPOOL_JOB')  -- daily 03:00

-- run one once, right now
SQL> EXEC DBMS_SCHEDULER.RUN_JOB('CAP_REPORT_SPOOL_JOB')

-- or write the snapshot by hand, no job needed
SQL> EXEC cap_report_spool('CAP_REPORTS')

-- check what happened
SQL> SELECT job_name, status, error#, actual_start_date
  2    FROM user_scheduler_job_run_details ORDER BY log_date DESC;

CAP_REFRESH_JOB runs cap_results.refresh (see Alert state). CAP_ML_RETRAIN keeps the Tier 2 models tracking the latest AWR days; it runs daily because a model older than esm_max_age_days drops out of the comparison. CAP_REPORT_SPOOL_JOB writes <report_dir>/cap_alerts.txt — a header with the timestamp, database and CRIT/WARN/INFO counts, then one pipe-delimited line per CAPR_ALERTS row in the order SEVERITY|KIND|DB_PDB|SERIES_KEY|DAY|VALUE|THRESHOLD|UNIT|MESSAGE, or a single OK|NONE|…|No capacity alerts. line when there is nothing to report. The file name is stable and overwritten on every run, so a poller can just read it.

i

The job writes alerts, not the report. SQL*Plus spooling cannot happen inside a scheduler job, so the formatted capacity report still comes from cron or your OS scheduler: report/run_report.sh (see CSV and cron). Use @uninstall_jobs.sql to remove the jobs and the procedure; it leaves the rest of the suite untouched.
