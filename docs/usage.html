Guide

Usage

Generate the read-only report, read it, drill into anything that looks wrong, poll the alert view from your monitoring stack, and tune everything through config rather than SQL.

The workflow is: run one script from the repo root, read its eight sections top to bottom, drill into any row you don't believe, wire CAPR_ALERTS into whatever already pages you, and turn every threshold through CAP_CONFIG. Nothing here writes to your AWR data.

Generate

Run the report

One script, run from the repo root. A bare run never prompts and spools a plain-text file.

SQL*Plusyou run
sqlplus / as sysdba              -- or any monitoring schema
SQL> @report/report.sql               -- everything from report/defaults.sql
SQL> @report/report.sql 5             -- top_n=5, the rest defaulted
SQL> @report/report.sql 5 7 N         -- top_n / anomaly_days / show_esm

Launch it from the repo root: SQL*Plus resolves @@ includes relative to the outermost caller on 19c, so report/report.sql must be started from the repository directory. It auto-loads report/defaults.sql, so a bare run never prompts, and it spools to reports/cap_report_<db>_<ts>.txt. The report is read-only — it only SELECTs, and creates or modifies no database object. Identity comes from SYS_CONTEXT, so no V$ or catalog privileges are needed.

The three positional arguments — [top_n] [anomaly_days] [show_esm]
PositionNameDefaultDoes
1top_n10Rows in the days-to-full, near-full, forecast and ESM-compare rankings.
2anomaly_days30Trailing days of anomalies printed in sections 3 and 5. Presentation only — CAPR_ALERTS has its own window, the anomaly_report_days knob (14).
3show_esmAUTOAUTO = show section 6 only if OK models exist, else print a one-line hint; Y = always show it; N = skip it. Case-insensitive.
▸

Presentation lives in one file — or on the command line. To change these three for every run, edit report/defaults.sql, the single source of truth both drivers load. To change one run, pass them positionally; an omitted argument falls back to that file, and neither form ever prompts. Both scripts UNDEFINE the arguments at the end, so a later argument-less call in the same session can't silently inherit them. Everything else is analytics config — see Configuration below.

Generate · alternative

HTML report

A sibling driver renders the same sections as one self-contained HTML dashboard instead of plain text — open the spooled file directly in a browser.

SQL*Plusyou run
sqlplus / as sysdba              -- run from the repo root
SQL> @report/report_html.sql        -- spools reports/cap_report_<db>_<ts>.html
SQL> @report/report_html.sql 25 60 Y  -- same three positional arguments

report/report_html.sql shares the same defaults file, the same knobs, and the same read-only guarantee as the text report — the HTML is assembled in one PL/SQL block via DBMS_OUTPUT and captured by SPOOL. It opens with a plain-English “At a glance” banner that says up front whether any tablespace, the whole database, or CPU is heading for trouble, then adds severity badges, quality pills, inline fill bars, and inline-SVG growth/trend charts (per-tablespace history + REGR projection + ESM +30 point and CI + limit line + anomaly markers; per-con_dbid host busy% and DB CPU charts with a saturation line). Every jargon column header carries a plain-English tooltip, and a collapsible glossary defines the terms — all rendered as plain <svg> with no JS chart library and no external assets, plus a sticky section nav and light/dark theming.

i

The two drivers read the same rows. Both consume the CAPR_ per-section views, where every derived number, label, severity marker and unit conversion is computed once; only chart geometry is calculated in the HTML driver. The text and HTML reports therefore cannot show different numbers.

Interpret

Reading the report

Eight sections, top to bottom, each backed by one CAPR_ view.

Sections 0–7 and the view behind each
#SectionWhat to read
0At a glance
CAPR_ALERTS		 CRIT / WARN / INFO counts, then one line per current issue: severity, kind, DB/PDB and a ready-to-page message. The same view the HTML banner and any external poller read, so they can never disagree. Its anomaly kinds use the anomaly_report_days knob, not this report's anomaly_days.
1Days-to-full & near-full
CAPR_TBSPC_DAYS_TO_FULL		 1a ranks tablespaces by days_to_full at any fit quality — a LOW_CONFIDENCE estimate is still a signal, and the QUALITY column says how far to trust it. CRIT at/below dtf_crit days, WARN at/below dtf_warn; ACCEL > 1.5 means growth is accelerating. WORST/BEST bound the estimate with the 95% CI on the slope (empty BEST = might never fill). 1b re-ranks by PCT_USED alone, independent of fit quality, so a 97%-full tablespace whose fit is unusable can never vanish from the report.
2Tablespace forecast
CAPR_TBSPC_FORECAST		 Current / +30 / +90 / +180 GiB with TRAIN_N, R², quality, and the ESM +30 column when Tier 2 models exist. 180_LO/180_HI are the 95% prediction band on the widest printed horizon. Bounded: a tablespace prints only if it is growing, near-full, or at least report_min_gb GiB used, then capped at top_n — the header states how many of the total it is showing.
3Tablespace anomalies
CAPR_TBSPC_ANOMALIES		 Flagged days inside anomaly_days, each fully justified: the day's growth rate (delta ÷ gap), the baseline median rate, the threshold max(k·MAD, 100 MiB/day floor), and the robust z. GAP is days since the previous sample — greater than 1 across an AWR gap, which is why the rate and not the raw delta is scored.
4CPU trend
CAPR_CPU_TREND		 Six metrics per container: BUSY_PCT (daily average), BUSY_P95 and BUSY_PEAK (the busy hour — p95 of the day's intervals, and the peak_hour_from/peak_hour_to window), plus DB_CPU_SEC, DB_CPU_PCT and DB_CPU_P95 for this container's DB CPU as a share of host core capacity. DAYS_SAT projects when the metric reaches cpu_sat_pct (every metric except DB_CPU_SEC, which has no percentage ceiling), with the same WORST/BEST slope-CI range.
5CPU anomalies & level shifts
CAPR_CPU_ANOMALIES · CAPR_CPU_SHIFTS		 5a scores busy% against a same-weekday median/MAD baseline, so weekly seasonality is handled deterministically rather than modelled. 5b catches the other failure mode: a sustained step rather than a one-day outlier. The recent window's median is compared with the baseline median before it, and flags only when the gap exceeds shift_min_pct points and every day of the recent window sits above (UP) or below (DOWN) the baseline median ± its MAD-sigma — the N-of-M column shows that count.
6ESM compare & backtest
CAPR_ESM_COMPARE · CAPR_BACKTEST		 6a tablespaces and 6b CPU, Tier 2 beside Tier 1 at each horizon with the ESM CI; ESM_MODEL names the variant (HOLT or ADDW, i.e. EXSM_ADDWINTERS with a 7-day season). 6c is the holdout scorecard — see Backtest below. 6a shows exactly the same tablespaces as section 2 (four horizons each). With show_esm=AUTO and no models, the whole section collapses to a one-line hint.
7Fixed-ceiling series
CAPR_SERIES		 Four series that share one property — each has, or conspicuously lacks, a single hard ceiling. PROCESSES and SESSIONS are peak concurrency (the AWR high-water mark since instance startup, summed across RAC instances) against the matching init parameter. REDO_GB_DAY is redo written per day; it has no ceiling and is a trend for FRA / archive-destination sizing. DB_SIZE_GB is total permanent-tablespace bytes used against the summed tablespace ceilings. DAYS_LIM projects when the series reaches series_sat_pct% of its limit — 90% by default, because hitting processes exactly is an outage, not a warning.
!

Read QUALITY before you read the number. Only OK is a trustworthy fit. LOW_CONFIDENCE means R² fell below r2_gate, FLAT means the slope is exactly zero, and INSUFFICIENT_HISTORY means fewer than min_train_days daily points — raise AWR retention, then wait. The report prints these loudly rather than quietly projecting a line it can't support.

Verify

Drill into one series

When a report row looks wrong, re-derive it with a pocket calculator.

SQL*Plus · repo rootyou run
SQL> @report/drill_tbspc.sql SYSAUX            -- name REQUIRED
SQL> @report/drill_tbspc.sql SYSAUX 2482321331 -- ... in one container only

SQL> @report/drill_cpu.sql                     -- BUSY_PCT, all containers
SQL> @report/drill_cpu.sql BUSY_P95
SQL> @report/drill_cpu.sql DB_CPU_PCT 2482321331

Each prints to screen and spools reports/cap_drill_<name>_<ts>.txt containing four blocks: the fit header (slope, intercept, R², the 95% slope CI, days-to-full or days-to-saturation with its WORST/BEST range); the daily series over the train_days window — actual, fitted icept + slope · day_n, residual, day-over-day delta, AWR gap and that day's median / MAD-sigma / threshold / robust-z; a residual footer showing SUM(residual) (zero by construction) and re-deriving resid_se = sqrt(SSE/(n−2)) and the slope CI from scratch next to the values the view publishes; and anomaly arithmetic, one spelled-out line per flagged day with the CAP_CONFIG knob values shown.

drill_cpu.sql's metric argument is optional and defaults to BUSY_PCT; the valid values are the six in section 4. Note that CAPA_CPU_ANOM scores the daily-average busy% only, so the anomaly columns read n/a for every metric except BUSY_PCT. drill_tbspc.sql requires a tablespace name — without one it prints usage and stops. Both are read-only, never prompt, and UNDEFINE their arguments at the end.

Integrate

Polling CAPR_ALERTS

The machine-readable surface: one row per current issue, shaped for an OEM metric extension, Zabbix, Nagios, or a scheduler job.

SQL*Plusexample
SQL> SELECT severity, kind, db_pdb, message
  2    FROM capr_alerts ORDER BY sev_rank;

-- alarm on the numbers, without parsing the message text
SQL> SELECT kind, db_pdb, series_key, value, threshold, unit
  2    FROM capr_alerts WHERE severity = 'CRIT';

Every row carries severity (CRIT/WARN/INFO) with a numeric sev_rank (1/2/3) to sort by, the kind, the (dbid, con_dbid) keys plus a resolved db_pdb label, the series_key (tablespace name, CPU metric or series name), the observation day_dt, the value that crossed its threshold with a unit, and a ready-to-page message. Alarm on value vs threshold; the message is for the human who gets paged.

The alert window is not the report window. The anomaly kinds use anomaly_report_days (14) from CAP_CONFIG; sections 3 and 5 of the report use the anomaly_days presentation knob (30). They are deliberately different: one bounds what pages you, the other bounds what you read.

Trust the ceiling

Reading limit_source, and overriding the limit

A days-to-full is only as honest as the limit it counts down to.

CAPF_TBSPC_FORECAST (and CAPR_TBSPC_FORECAST above it) publishes limit_source, which says where that ceiling came from:

limit_source — three possible answers
ValueMeans
OVERRIDEA CAP_TBSPC_OVERRIDE row set the ceiling by hand. This one you can trust, because you wrote it.
AUTOEXTENDThe summed datafile maxsize recorded in AWR. Trustworthy only if the storage underneath can actually deliver it.
ALLOCATEDNo autoextend — the currently allocated size is the ceiling.
!

AUTOEXTEND is a promise the storage may not keep. A 32 GiB datafile maxsize on a 10 GiB filesystem or ASM diskgroup is not 32 GiB of headroom, and a days-to-full computed against it is a comfortable lie. When you know the real ceiling, state it.

Tune · per tablespace

CAP_TBSPC_OVERRIDE

Set the real ceiling, or silence the staging tablespace that is supposed to fill up. MERGE so the statement is re-runnable.

SQL*Plusexample
-- the real ceiling is the 200 GiB diskgroup, not the 2 TB datafile maxsize
MERGE INTO cap_tbspc_override t
USING (SELECT 1234567890 AS dbid,
              2345678901 AS con_dbid,
              'APPDATA'  AS tablespace_name,
              200 * 1024 * 1024 * 1024 AS limit_bytes,
              'N'        AS exclude_flag,
              'DG +DATA is 200G; maxsize is fiction' AS note
       FROM   dual) s
ON     (t.dbid = s.dbid AND t.con_dbid = s.con_dbid
        AND t.tablespace_name = s.tablespace_name)
WHEN MATCHED THEN UPDATE
     SET t.limit_bytes  = s.limit_bytes,
         t.exclude_flag = s.exclude_flag,
         t.note         = s.note
WHEN NOT MATCHED THEN
     INSERT (dbid, con_dbid, tablespace_name, limit_bytes, exclude_flag, note)
     VALUES (s.dbid, s.con_dbid, s.tablespace_name,
             s.limit_bytes, s.exclude_flag, s.note);

-- stop forecasting the nightly-truncated staging tablespace, in EVERY database
MERGE INTO cap_tbspc_override t
USING (SELECT 0 AS dbid, 0 AS con_dbid, 'STAGING' AS tablespace_name,
              CAST(NULL AS NUMBER) AS limit_bytes, 'Y' AS exclude_flag,
              'reloaded nightly -- growth is meaningless' AS note
       FROM   dual) s
ON     (t.dbid = s.dbid AND t.con_dbid = s.con_dbid
        AND t.tablespace_name = s.tablespace_name)
WHEN MATCHED THEN UPDATE
     SET t.limit_bytes  = s.limit_bytes,
         t.exclude_flag = s.exclude_flag,
         t.note         = s.note
WHEN NOT MATCHED THEN
     INSERT (dbid, con_dbid, tablespace_name, limit_bytes, exclude_flag, note)
     VALUES (s.dbid, s.con_dbid, s.tablespace_name,
             s.limit_bytes, s.exclude_flag, s.note);

COMMIT;
How a row is matched
ColumnRule
tablespace_nameMatched exactly. No patterns, no wildcards.
dbid · con_dbid0 is a wildcard meaning "any". So (0, 0, 'STAGING') is a fleet-wide rule, (dbid, 0, 'STAGING') is per-database, and naming both is per-container.
most specific winsWhen several rows match one tablespace, a real dbid beats the 0 wildcard first, then a real con_dbid does.
limit_bytesThe real ceiling in bytes. NULL keeps the computed limit — useful on a row that exists only to set exclude_flag.
exclude_flag'Y' drops the tablespace from CAPD_TBSPC_DAILY and therefore from forecasts, anomalies, alerts and both reports. Defaults to 'N'.
noteFree text, for whoever reads the table in six months.

The override is applied once, in CAPD_TBSPC_DAILY, so every layer above it honours it automatically — no re-install, no view change. Your rows survive @install.sql and are removed only by @uninstall.sql.

Optional · Tier 2

Tier 2 (OML ESM)

Train one Oracle Machine Learning model per series for a seasonality-aware second opinion, then re-run the report to populate section 6.

SQL*Plusyou run
SQL> EXEC cap_forecast_ml.train_all(20);       -- top-20 tablespaces + CPU series
SQL> EXEC cap_forecast_ml.train_backtest(20);  -- optional holdout twins for 6c
SQL> @report/report.sql                        -- section 6 now shows ESM vs REGR

SQL> EXEC cap_forecast_ml.drop_all;            -- remove the models again

Training needs the CREATE MINING MODEL privilege (free in all editions since Dec 2019). With esm_tbspc_model at its default of AUTO, train_all trains both EXSM_HOLT and EXSM_ADDWINTERS(7) as holdout twins per tablespace and keeps whichever scored the lower backtest MAPE — set esm_select_by_backtest to 0 to skip those two extra trainings and let AUTO fall back to Holt, or pin the type outright with 0 or 1. To automate the refresh, see Scheduler jobs below.

!

Tier 2 only ever reaches +30 days. Oracle 19c hard-caps EXSM_PREDICTION_STEP at 30 at any series length, so ESM forecasts stop at +30; the +90 / +180 / +365 columns in CAPF_COMPARE are always REGR-only. The package caps the step automatically — it never fails, it just doesn't reach further.

Interpret · section 6c

Reading the backtest

Which engine was actually right, over a window where you already know the answer.

Section 6c replays the recent past: each engine forecasts the last backtest_holdout_days (28) from data before the cutoff, and is scored against what really happened. MAPE% is the mean absolute percentage error — lower is better. BIAS% is signed: positive means the engine over-forecast. BETTER names the engine with the lower MAPE, and is empty when one of the two has no score to compare. CUTOFF is the day the holdout starts.

ESM_PICK explains the AUTO decision in one column: either ADDW H=2.90 W=1.20 — the chosen type followed by the Holt and AddWinters MAPEs that decided it — or HOLT (config) when the type was pinned by esm_tbspc_model instead of measured.

i

REGR is scored with or without models; ESM needs the twins. The REGR_MAPE / REGR_BIAS columns work on a fresh install — CAPF_BACKTEST is queryable any time. The ESM columns fill only after cap_forecast_ml.train_backtest. Expect ESM to cover fewer days than REGR: the backtest twins inherit both the 19c 30-step cap and the package's FLOOR(rows/4) floor, and n_days reports the coverage each engine actually achieved.

Configuration

Every threshold lives in CAP_CONFIG, read by the views through a one-row cfg CTE. Tuning never means editing SQL, and never means re-installing.

SQL> UPDATE cap_config SET cfg_value = 0.70 WHERE cfg_name = 'r2_gate';
SQL> COMMIT;
SQL> SELECT * FROM cap_config ORDER BY cfg_name;   -- the full annotated list

Tune · the estimator

Switching to Theil–Sen

One knob swaps the slope estimator for every CAPF_ fit.

SQL*Plusexample
SQL> UPDATE cap_config SET cfg_value = 1 WHERE cfg_name = 'slope_method';
SQL> COMMIT;   -- 0 = OLS (default), 1 = Theil-Sen

-- both estimators are always exposed; compare them per tablespace
SQL> SELECT tablespace_name, slope_method, ols_slope_bpd, ts_slope_bpd
  2    FROM capf_tbspc_forecast ORDER BY tablespace_name;

CAP_CONFIG is numeric, so the encoding is 0 = OLS (REGR_SLOPE, the default) and 1 = THEILSEN, the median of the pairwise slopes. Theil–Sen is worth reaching for when a series carries a one-off step — a bulk load, a migration — that drags a least-squares line off the underlying trend. The chosen estimator drives the slope, intercept, projections, days-to-full, days-to-saturation, accel_ratio and the FLAT test; the slope_method column on each row says which one that row used, and both slopes stay visible as ols_slope_bpd and ts_slope_bpd so you can see what changed.

i

R² and the prediction bands stay OLS. There is no closed-form Theil–Sen interval in SQL, so r2, resid_se, the projection bands and the slope CI remain OLS residual quantities — drawn around whichever line you chose. That is a deliberate v1 trade-off, not an oversight.

▸

A related knob for the other kind of step. Where Theil–Sen tolerates a step, reset_on_shrink (on by default) removes one: after the most recent large shrink in a tablespace, the training window restarts at that day — its used_bytes is already post-purge — so the fit describes the series as it is now rather than averaging across the cliff. shrink_mad_k (6) sets how big a drop has to be to count; it is deliberately higher than mad_k because it restarts a fit.

Automate

Scheduler jobs

Optional, and installed separately — see Installation for the setup and the directory-object requirement.

SQL*Plusyou run
-- both jobs arrive DISABLED; enable whichever you want
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_ML_RETRAIN')       -- Sun 02:00
SQL> EXEC DBMS_SCHEDULER.ENABLE('CAP_REPORT_SPOOL_JOB')  -- daily 03:00

-- run one once, right now
SQL> EXEC DBMS_SCHEDULER.RUN_JOB('CAP_REPORT_SPOOL_JOB')

-- or write the snapshot by hand, no job needed
SQL> EXEC cap_report_spool('CAP_REPORTS')

-- check what happened
SQL> SELECT job_name, status, error#, actual_start_date
  2    FROM user_scheduler_job_run_details ORDER BY log_date DESC;

CAP_ML_RETRAIN keeps the Tier 2 models tracking the latest AWR days. CAP_REPORT_SPOOL_JOB writes <report_dir>/cap_alerts.txt — a header with the timestamp, database and CRIT/WARN/INFO counts, then one pipe-delimited line per CAPR_ALERTS row in the order SEVERITY|KIND|DB_PDB|SERIES_KEY|DAY|VALUE|THRESHOLD|UNIT|MESSAGE, or a single OK|NONE|…|No capacity alerts. line when there is nothing to report. The file name is stable and overwritten on every run, so a poller can just read it.

i

The job writes alerts, not the report. SQL*Plus spooling cannot happen inside a scheduler job, so the formatted capacity report still comes from sqlplus … @report/report.sql driven by cron or your OS scheduler. Use @uninstall_jobs.sql to remove both jobs and the procedure; it leaves the rest of the suite untouched.

For the non-obvious behaviours these knobs interact with — AWR retention, the flat-series REGR_R2 quirk, block-size sourcing, the ESM cap — and the full index of every object the suite creates, see the Reference page.
