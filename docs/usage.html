Guide

Usage

Generate the read-only report, read it, optionally add the Tier 2 second opinion, and tune everything through config rather than SQL.

The whole workflow is four moves: run one script from the repo root, read its six sections top to bottom, add the optional OML forecast when you want a second opinion, and turn every threshold through CAP_CONFIG. Nothing here writes to your AWR data.

Generate

Run the report

One script, run from the repo root. A bare run never prompts and spools a plain-text file.

SQL*Plusyou run
sqlplus / as sysdba              -- or any monitoring schema
SQL> @report/report.sql               -- defaults
SQL> @report/report.sql 5 7 N         -- top_n / anomaly_days / show_esm

Launch it from the repo root: SQL*Plus resolves @@ includes relative to the outermost caller on 19c, so report/report.sql must be started from the repository directory. report.sql auto-loads report/defaults.sql, so a bare run never prompts, and it spools to reports/cap_report_<db>_<ts>.txt. The report is read-only — it only SELECTs, and creates or modifies no database object. Identity comes from SYS_CONTEXT, so no V$ or catalog privileges are needed.

▸

Presentation lives in one file — or on the command line. To change top_n, anomaly_days, or show_esm for every run, edit report/defaults.sql — the single source of truth for presentation. To change one run, pass them positionally: @report/report.sql [top_n] [anomaly_days] [show_esm] (same for report_html.sql); an omitted argument falls back to that file. Everything else is analytics config (see below).

▸

Drill into one series. When a row looks wrong, @report/drill_tbspc.sql SYSAUX (name required) and @report/drill_cpu.sql BUSY_P95 (metric optional, default BUSY_PCT; both take an optional con_dbid) print and spool reports/cap_drill_<name>_<ts>.txt: the fit header, the daily series with fitted value, residual, delta, gap and the day's anomaly baseline, a residual footer that re-derives resid_se and the slope CI from scratch, and one spelled-out arithmetic line per flagged day. Read-only, and never prompts.

Generate · alternative

HTML report

A sibling driver renders the same six sections as one self-contained HTML dashboard instead of plain text — open the spooled file directly in a browser.

SQL*Plusyou run
sqlplus / as sysdba              -- run from the repo root
SQL> @report/report_html.sql     -- spools reports/cap_report_<db>_<ts>.html

report/report_html.sql shares the same defaults file, the same knobs, and the same read-only guarantee as the text report — the HTML is assembled in one PL/SQL block via DBMS_OUTPUT and captured by SPOOL. It opens with a plain-English “At a glance” banner that says up front whether any tablespace, the whole database, or CPU is heading for trouble, then adds severity badges, quality pills, inline fill bars, and inline-SVG growth/trend charts (per-tablespace history + REGR projection + ESM +30 point and CI + limit line + anomaly markers; per-con_dbid host busy% and DB CPU charts with a saturation line). Every jargon column header carries a plain-English tooltip, and a collapsible glossary defines the terms — all rendered as plain <svg> with no JS chart library and no external assets, plus a sticky section nav and light/dark theming.

Interpret

Reading the report

Six sections, top to bottom. Every section consumes only the CAPF_* / CAPA_* views.

#SectionWhat to read
1Days-to-full rankingTop-N tablespaces by days_to_full. WARN under 90 days, CRIT under 30. An accel_ratio > 1.5 means growth is accelerating.
2Tablespace forecastCurrent / +30 / +90 / +180 GB, with R² and quality — and ESM +30 when models exist.
3Tablespace anomaliesLast N days, each row fully justified: value, median, MAD·k threshold, robust z.
4CPU trendbusy% current / slope / days-to-80%, plus the DB CPU-seconds trend.
5CPU anomaliesSame-day-of-week MAD baseline — weekly seasonality handled deterministically.
6ESM compareTier 2 vs Tier 1 at +30. With show_esm=AUTO and no models, prints a one-line hint instead.
Optional · Tier 2

Tier 2 (OML ESM) — optional

Train one Oracle Machine Learning model per series for a seasonality-aware second opinion, then re-run the report to populate section 6.

SQL*Plusyou run
SQL> EXEC cap_forecast_ml.train_all(20);   -- top-20 tablespaces + CPU series
SQL> @report/report.sql                     -- then section 6 shows ESM vs REGR

Training needs the CREATE MINING MODEL privilege (free in all editions since Dec 2019). cap_forecast_ml.drop_all removes the models again. A weekly DBMS_SCHEDULER retrain job is documented (shipped commented-out) in docs/design.md.

!

Tier 2 only ever reaches +30 days. Oracle 19c hard-caps EXSM_PREDICTION_STEP at 30, so ESM forecasts stop at +30; the +90 / +180 / +365 columns in CAPF_COMPARE are always REGR-only. The package caps the step automatically.

Tune

Configuration

Every threshold lives in CAP_CONFIG, read by the views through a one-row cfg CTE. Tuning never means editing SQL.

SQL*Plusexample
SQL> UPDATE cap_config SET cfg_value = 0.70 WHERE cfg_name = 'r2_gate';
SQL> SELECT * FROM cap_config ORDER BY cfg_name;   -- the full annotated list
KnobDefaultControls
train_days90primary fit window
recent_days28"recent" fit window (for accel_ratio)
min_train_days14below this → INSUFFICIENT_HISTORY
r2_gate0.60below this → LOW_CONFIDENCE
mad_k3MAD-sigma multiplier for anomaly threshold
mad_window_days28trailing anomaly baseline window
cpu_sat_pct80CPU saturation target for days-to-sat
abs_floor_bytes100 MiBmin growth/day to flag (flat-baseline guard)
dow_weeks8same-weekday baseline depth for CPU anomalies
dtf_warn / dtf_crit90 / 30days-to-full WARN / CRIT thresholds

For the non-obvious behaviours these knobs interact with — AWR retention, the flat-series REGR_R2 quirk, block-size sourcing, the ESM cap — and the full index of every object the suite creates, see the Reference page.
